## 1. 最小前置知识：先能看懂数字和代码

### 1.1 bit、Byte、KB、KiB：别把容量和速度混在一起

**前置：**会做乘除法即可。

计算机最终用 0 和 1 表示信息。一个这样的二进制位叫 **bit（比特，缩写 b）**；8 个 bit 组成一个 **Byte（字节，缩写 B）**。

```text
1 Byte = 8 bit
1 kB = 1,000 Byte         1 KiB = 1,024 Byte
1 MB = 1,000,000 Byte     1 MiB = 1,048,576 Byte
1 Mb/s = 1,000,000 bit/s
```

网络速率常用十进制 bit/s；内存大小常用 Byte。日常界面中的“KB”可能含义不清，做计算时写出明确单位。本章 MB 一律使用十进制。

例子：4 Mb/s 的视频，每秒平均只有 `4,000,000 ÷ 8 = 500,000 Byte = 0.5 MB` 的视频压缩数据。持续 60 秒，约 30 MB；还没计入音频、容器和网络开销。

“每秒”表示**速率**，“总共”表示**容量**。码率 4 Mb/s、文件 30 MB、时长 60 s 是三个不同量。

**常见错误：**把 4 Mbps 写成每秒 4 MB，会高估 8 倍；把 MiB 与 MB 混用，会产生约 4.86% 的差异。

**练习：**8 Mb/s 的纯视频录制 10 分钟，压缩数据约多大？先换算为 Byte/s，再乘秒数。答案在 §13。

### 1.2 为本章准备的最少 C++ 知识

**前置：**能创建文本文件、能在终端输入命令。不会这些也可以先完成 §3。

本章使用 C++17，不依赖第三方 C++ 库。第一次遇到下面写法时，可按右侧含义阅读：

| 写法 | 通俗解释 | 本章为什么使用 |
|---|---|---|
| `int main()` | 程序从这里开始执行 | 每个 `.cpp` 都是单独程序 |
| `std::uint8_t` | 通常用来装一个 0～255 的字节 | 保存像素、文件和压缩流字节 |
| `std::uint32_t` | 精确 32 位的无符号整数 | WAV 字段、RTP 时间戳 |
| `std::int64_t` / `std::uint64_t` | 精确 64 位的有/无符号整数 | 时间与数据量计算，减少溢出 |
| `std::vector<T>` | 一段能自动管理内存的连续数组 | 保存一帧的像素 |
| `std::ofstream` | 向文件写数据的工具 | 生成图片、音频；需二进制模式 |
| `static_cast<T>(x)` | 明确把 x 转为类型 T | 控制整数、浮点数和字节之间的转换 |
| `return 0` / `return 1` | 正常结束 / 报告失败 | 在 PowerShell 中看 `$LASTEXITCODE` |

**整数除法**会丢弃小数部分。例如 `1 / 30` 得到 0，而 `1.0 / 30` 得到约 0.033333。算平均帧间隔时，需要浮点数或保留分数。

**溢出**就是容器装不下数字。例如 8 位无符号整数不能表示 256。表达式如果先用 32 位整数相乘，最后再放进 64 位变量，也可能已经溢出，所以应从运算开始就使用 `std::uint64_t` 等足够宽的类型。

本章代码默认 Windows 常见的 8 位字节平台。对于真实媒体，不能简单地把一个 C++ 结构体的内存直接写入文件：结构体可能有填充字节，不同文件格式还规定了字节顺序。§6 会手动按顺序写 WAV 字段。

**常见错误：**复制多个含有 `main()` 的示例到一个文件，导致重复定义；将 `uint8_t` 直接送给 `std::cout`，结果显示为字符；忘记写 `std::ios::binary`。

## 2. 先建立全景：播放器在处理什么

**前置：**§1。此处先理解流程，不要求会调用任何音视频库。

摄像头先获得画面，麦克风先获得声音。未压缩的数据叫**原始数据**；将其压小的过程叫**编码**，按照约定恢复出可显示、可播放数据的过程叫**解码**。有损压缩一般无法恢复每一个原始数值，但能尽量保留视觉和听觉信息。

```text
发送端：摄像头/麦克风 → 原始图像/声音 → 编码器 → 压缩数据 → 封装或网络打包
接收端：文件/网络 → 解封装或网络解包 → 压缩数据 → 解码器 → 原始图像/声音
                                                               ↓
                                                 画面显示 / 声卡播放
```

一个典型 RTSP 客户端还包含：

```text
RTSP 协商会话 → SDP 告诉你媒体格式 → RTP 搬运音视频数据
                                        ↓
                              重排、去头、重组压缩数据
                                        ↓
                        解码 → 像素/音频格式转换 → 按时间播放
RTCP 提供传输报告和时钟对应关系 ──────────────┘
```

RTSP 像“遥控器”，负责建立和控制播放会话；RTP 像“运货车”，通常承载媒体；H.264 是“货物如何压缩”的约定。RTP 可以经 UDP 传输，也可以按 RTSP 的交织方式经 TCP 传输。协议细节以后再学，先区分职责。

还要区分三个容易都叫“帧/包”的对象：

| 对象 | 大致含义 | 是否能直接当成一张图片 |
|---|---|---|
| 网络包 | 一次网络传送中的数据单元 | 通常不能；可能只是压缩图像的一小段 |
| 压缩数据包 | 交给编码器/解码器接口的字节及时间信息 | 需要解码；边界依赖格式和接口 |
| 解码后的帧 | 像素数据或一批音频样本，外加格式信息 | 视频可经必要转换后显示 |

一个 TCP `recv()` 返回值不是一帧；一个 RTP 包也不一定是一帧。即使一个 H.264 NAL 完整，也不代表一张图像完整。

**常见错误：**试图把 H.264 压缩字节当作 RGB 显示；认为换成 TCP 就不用处理媒体边界；认为 MP4 扩展名足以说明内部编码。

## 4. 视频基础：一串图片为什么会动

### 4.1 分辨率、宽高比、逐行与隔行

**前置：**§1 的数据单位，§2 的视频帧概念。

一张数字图片由小格子组成，每个小格子叫**像素（pixel）**。分辨率通常写成 `宽 × 高`：1920×1080 表示每行 1920 个像素，共 1080 行，总计 2,073,600 个像素。

分辨率只表示空间采样数量，不直接保证清晰度；镜头、对焦、噪声、缩放和压缩都会影响最终画面。

**画面宽高比**表示显示出来有多宽、多高。1920÷1080 = 16÷9，是常见的 16:9。以方形像素为前提，把 16:9 强行拉成 4:3，人脸就会变形。某些媒体的像素不是方形，还要看 SAR（单个像素的宽高比）与 DAR（最终显示宽高比）；初学实验使用方形像素即可。

`1080p` 中的 p 表示**逐行扫描（progressive）**，每帧包含整张图。`1080i` 中的 i 表示**隔行扫描（interlaced）**，相邻的场分别保存交替的行；场率与帧率不能直接混为一谈。播放运动隔行内容可能需要去隔行，否则容易看到梳齿边缘。本章全部使用逐行素材。

**常见错误：**认为宽高翻倍只是数据翻倍；实际上像素数变为 4 倍。

**练习：**1280×720 有多少像素？与 1920×1080 相比，像素数比值是多少？

### 4.2 帧率、帧间隔、CFR 与 VFR

**前置：**知道一帧是一张图，且整数除法会截断。

**帧率 fps（frames per second）**表示每秒多少帧。30 fps 表示平均每秒显示 30 张图；在固定帧率下，每帧间隔约 `1/30 s = 33.333 ms`。60 fps 对应约 16.667 ms。

**CFR**是恒定帧率，时间间隔固定；**VFR**是可变帧率，帧与帧的时间间隔可以不同。手机录屏或屏幕录制可能是 VFR。真实播放应该按照时间戳调度，而不能总靠 `sleep(33)`。

29.97 fps 通常是 `30000/1001` 的近似写法；不是精确 30。持续使用错误帧率推算时间，会慢慢产生偏差。

帧率不是网络每秒的包数，也不是显示器刷新率。例如 30 fps 的视频可在 60 Hz 显示器上重复显示每张图，但不会凭空多出 30 张新的运动画面。刷新率与帧率不匹配还可能造成顿挫。

**练习：**25 fps 的固定帧率视频，每帧应持续多少毫秒？2 秒应有多少帧？

### 4.3 原始数据量、码率与文件大小

**前置：**§1 单位换算、§4.1 像素数。

先假设每个像素用 R/G/B 三个通道、每个通道 1 Byte 保存；这叫 8 位 RGB24，详见 §5。若每行没有额外填充：

```text
一帧 RGB24 字节数 = 宽 × 高 × 3
原始视频 bit/s = 一帧字节数 × fps × 8
压缩后媒体大小 ≈ 平均码率 bit/s × 时长 s ÷ 8
```

1920×1080、30 fps 的 RGB24：

```text
一帧 = 1920 × 1080 × 3 = 6,220,800 Byte
每秒 = 6,220,800 × 30 = 186,624,000 Byte/s = 186.624 MB/s
码率 = 1,492,992,000 bit/s ≈ 1.493 Gb/s
```

真实内存还可能有行对齐或多个平面，不能只按这个公式分配所有解码器输出。这里先使用紧密排列的简单图像。

**码率（bitrate）**表示每秒多少 bit。它可以指压缩视频码率、音频码率或总传输速率，讨论时要说明对象。分辨率相同也可能有不同压缩码率。

码率相同不代表画质相同：运动复杂度、噪声、编码格式和编码器设置都会影响质量。**CBR**以控制码率较稳定为目标，**VBR**允许复杂画面分配更多数据；短时间窗口仍可能出现突发。**CRF**是部分编码器提供的质量控制方式，给定质量目标后码率随内容变化，不能把某个 CRF 值直接当作固定 Mb/s。

## 5. 像素与显示：同一张图为什么有不同存法

### 5.1 RGB、BGR、RGBA 与位深

**前置：**§4 中的像素、分辨率和一帧大小。

RGB 分别是 Red、Green、Blue，即红、绿、蓝三个通道。对于 8 位通道，每个数取 0～255。`(255,0,0)` 是红色，`(0,255,0)` 是绿色，`(255,255,255)` 是白色。

**RGB24**表示一个像素共 24 bit，也就是三个 8 位通道；不是每个通道 24 bit。**BGR24**保存相同含义的数据，只是顺序为蓝、绿、红。顺序弄反时，最明显的现象是红蓝互换。

**RGBA/BGRA**多一个 alpha 通道，通常用来表达透明度。8 位 RGBA 共 32 bit，即 4 Byte/像素。10 位、12 位视频则需要更高精度存储，不能直接套用 8 位视频的一帧字节公式。

### 5.2 stride / linesize：一行未必正好是宽乘 3

**前置：**会按数组下标访问字节。

**stride（行跨度）**是从一行的开头走到下一行开头需要跨过的字节数。FFmpeg 常用 `linesize` 表达各平面的行跨度。

以宽为 3 的 RGB24 图片为例：一行有效数据是 9 Byte，但某个接口可能按 4 Byte 对齐，实际每行占 12 Byte，末尾补 3 Byte。访问 `(x,y)` 的常见方式是：

```text
偏移 = y × stride + x × 每像素字节数
```

不能总是用 `y × width × 3`。真实接口还可能给出负的行跨度，表示反向行序；应按接口契约处理。不同平面的 stride 也可能不同。

**常见错误：**忽略对齐后，第一行正确、后面逐行错位；把 BGR 认成 RGB；把底向上排列的图片按顶向下读取。

**练习：**宽 5、高 2 的 RGB24，若每行按 4 字节对齐，stride 是多少？总存储多少字节？有效像素数据又是多少？

### 5.3 实验二：不依赖图像库，生成一张 RGB 图片

**目标：**证明图片就是“尺寸、格式说明和像素字节”。使用简单的 **PPM P6** 文件格式：文本头说明宽高和最大通道值，后面紧跟 RGB 字节。文件：`make_rgb.cpp`。

```cpp
#include <cstdint>
#include <fstream>
#include <iostream>
#include <vector>

int main() {
    const int width = 320;
    const int height = 240;
    const int stride = width * 3; // Tightly packed RGB24 in this example.
    std::vector<std::uint8_t> pixels(
        static_cast<std::size_t>(stride) * height);

    for (int y = 0; y < height; ++y) {
        for (int x = 0; x < width; ++x) {
            const auto offset = static_cast<std::size_t>(y) * stride + x * 3;
            pixels[offset] = static_cast<std::uint8_t>(x * 255 / (width - 1));
            pixels[offset + 1] = static_cast<std::uint8_t>(y * 255 / (height - 1));
            pixels[offset + 2] = 64;
        }
    }

    std::ofstream file("gradient.ppm", std::ios::binary);
    if (!file) {
        std::cerr << "Cannot open gradient.ppm\n";
        return 1;
    }
    file << "P6\n" << width << ' ' << height << "\n255\n";
    file.write(reinterpret_cast<const char*>(pixels.data()),
               static_cast<std::streamsize>(pixels.size()));
    file.close();
    if (!file) {
        std::cerr << "Write failed\n";
        return 1;
    }
    std::cout << "Wrote gradient.ppm, pixel bytes: " << pixels.size() << '\n';
}
```

按 §3 编译运行 `make_rgb.cpp`，应打印 `pixel bytes: 230400`，生成 230,415 Byte 的 `gradient.ppm`（多出的 15 Byte 是文件头）。

```powershell
Get-Item .\gradient.ppm | Select-Object Name,Length
ffplay -autoexit -i .\gradient.ppm
```

图像左侧红通道低、右侧红通道高；上方绿通道低、下方绿通道高；蓝通道恒为 64。静态图片可能很快结束播放，也可用支持 PPM 的图像查看器。Windows 默认“照片”不一定支持 PPM；有 FFmpeg 时可转换：

```powershell
ffmpeg -n -i .\gradient.ppm -frames:v 1 .\gradient.png
```

`-n` 表示已存在输出时停止，避免无意覆盖；重做时改文件名即可。本章其他 FFmpeg 输出命令也遵守这个规则。

**练习：**让所有像素变为纯红，再改为纯绿。之后交换红蓝写入位置，观察颜色如何变化。改尺寸时保证宽高均大于 1，避免代码中的除零。

### 5.4 YUV、YCbCr、4:2:0 与平面布局

**前置：**RGB、每通道 8 位、像素数组。

数字视频里经常把 YCbCr 口头简称为 YUV。这里先这样理解：**Y 保存明暗相关信息，Cb/Cr 保存颜色偏离信息**。严格说数字视频中的 Y 通常是经过非线性处理后的亮度信号（luma），不等于物理测量中的亮度。

人眼通常对明暗细节更敏感，对颜色细节相对不敏感，所以可以让多个像素共用较少的颜色样本，这叫**色度抽样**：

| 常见标记 | 对于一个 2×2 像素区域 | 8 位紧密存储的典型数据量 |
|---|---|---|
| 4:4:4 | 4 个 Y、4 个 Cb、4 个 Cr | 3 Byte/像素 |
| 4:2:2 | 4 个 Y、2 个 Cb、2 个 Cr | 2 Byte/像素 |
| 4:2:0 | 4 个 Y、1 个 Cb、1 个 Cr | 1.5 Byte/像素 |

这里只解释常见布局的样本数量，不表示“4:2:0 是四个像素中丢掉两个像素”。明暗信息仍按每个像素保留。

**YUV420P / I420**是常见的三个平面布局：先存全部 Y，再存全部 U（Cb），最后存全部 V（Cr）。对于偶数宽 W、偶数高 H：

```text
Y 平面：W × H Byte
U 平面：(W/2) × (H/2) Byte
V 平面：(W/2) × (H/2) Byte
总共：W × H × 3/2 Byte
```

奇数尺寸需要向上取整色度尺寸；不能用简单的整数 `W*H*3/2` 代替所有情况。实验统一用偶数宽高。

**NV12**也是 4:2:0，但由一个 Y 平面和一个 UV 交错平面组成：`U0 V0 U1 V1 ...`。与 YUV420P 样本量相同，内存布局不同。**NV21**则为 VU 顺序。不能因为总字节数相同就互相当作对方。

### 5.5 色彩转换还需要哪些信息

**前置：**知道 Y 与 Cb/Cr 分开存储。

仅知道“YUV420P”不足以准确转成 RGB，还要知道：

- **转换矩阵**：BT.601、BT.709、BT.2020 等规定不同颜色关系。分辨率有常见搭配，但不能仅凭分辨率猜测，优先读媒体元数据。
- **范围 range**：8 位有限范围常见 Y 为 16～235、Cb/Cr 为 16～240；全范围通常使用 0～255。范围解释不一致，常表现为黑位发灰或暗部细节丢失。
- **色度采样位置**：颜色样本与亮度样本如何对齐；错误时可能出现彩边。
- **色原色与传递特性**：决定颜色基准和数值到亮度的映射，HDR 中尤其重要；本章先使用普通 SDR。

仅为理解 BT.601、8 位有限范围，可看以下近似公式；不要把它当作所有素材的通用转换器：

```text
R ≈ 1.164 × (Y−16) + 1.596 × (Cr−128)
G ≈ 1.164 × (Y−16) − 0.392 × (Cb−128) − 0.813 × (Cr−128)
B ≈ 1.164 × (Y−16) + 2.017 × (Cb−128)
```

结果要舍入并限制在 0～255。实际开发通常让 `libswscale` 等库根据元数据转换，详见 [[08-FFmpeg与解码]]。

## 6. 音频基础：声音怎样变成整数

### 6.1 采样率：每秒记录多少次

**前置：**§1 的速率与容量，知道声音随时间变化。

现实声音是连续变化的。计算机每隔一小段时间测量一次，得到一个数字，叫**采样（sample）**。**采样率**表示每个声道每秒采多少次，单位 Hz；48 kHz 就是每声道每秒 48,000 次。

采样率不是音调。440 Hz 的音调表示波形每秒重复 440 次；48,000 Hz 采样率表示每秒对这个波形记录 48,000 个数。

理想条件下，采样率应大于希望保留的最高频率的两倍；实际还需要滤波和余量。若不处理过高频率，会出现**混叠**，即高频被错误地表现成低频。你暂时无需推导公式，只需知道“采样不足会错误记录声音”。

### 6.2 位深、量化、声道与 PCM

**前置：**bit/Byte 和有符号整数。

**量化**就是把连续振幅放进有限的数字刻度；**位深**决定这些刻度有多少。例如有符号 16 位整数样本范围为 −32768～32767。位深更高可以提高可表示的精细程度，但不自动保证录音更好。

**PCM（脉冲编码调制）**在这里指直接保存这些采样值的一类原始音频表示。常见数据可能是有符号 16 位整数，也可能是 32 位浮点；浮点音频常用约 −1.0～1.0 表示正常幅度范围，但中间处理结果也可能超出此范围。

**声道**表示同时记录的声音通路：单声道为 1，立体声通常为 2（左 L、右 R）。立体声不是采样率翻倍；每个声道仍各有自己的采样序列。

相同采样时刻各声道的一组样本，也常叫一个 **PCM sample frame（采样帧）**。例如 48 kHz 立体声，一秒有 48,000 个采样帧、96,000 个单声道采样值。这里的“帧”不是视频画面，也不是编码器每次处理的一大块音频。

**交错 interleaved**布局：`L0 R0 L1 R1 ...`；**平面 planar**布局：左声道一整块、右声道另一整块。FFmpeg 的音频样本格式中，尾部 `p` 通常表示 planar，例如 `fltp` 是浮点平面格式。交给声卡前可能需要转换布局。

### 6.3 PCM 数据量与编码音频帧

**前置：**采样率、声道数、位深。

若每个样本按位深紧密存储：

```text
PCM Byte/s = 采样率 × 声道数 × 位深 ÷ 8
48 kHz、双声道、16 位 = 48000 × 2 × 16 ÷ 8 = 192,000 Byte/s
PCM bit/s = 1,536,000 bit/s = 1.536 Mb/s
```

某些 24 位音频可能使用 32 位容器保存，真实字节数应按接口规定的存储格式计算，不能只看有效精度。

AAC、Opus 等把一批样本压缩成编码数据。一个**编码音频帧**往往对应连续一段时间：

```text
该帧时长 = 每声道样本数 ÷ 采样率
AAC-LC 常见 1024 个样本/声道：1024 ÷ 48000 ≈ 21.333 ms
20 ms 的 48 kHz 音频：48000 × 0.020 = 960 个样本/声道
```

不是所有 AAC 配置都固定 1024，也不是所有 Opus 包都固定 20 ms。一个网络包还可以承载多个音频帧；最终应读格式和包的实际信息。

**音频重采样**是改变采样率，例如从 44.1 kHz 转为 48 kHz，需要插值与滤波，不是只改文件头中的数字。只改声明而不改样本，速度、时长和音调会出错。

### 6.4 实验四：用 C++ 写出可播放的 WAV

**目标：**生成 2 秒、48 kHz、单声道、16 位 PCM 的 440 Hz 正弦波。WAV 是容器；本例用它包住 PCM，便于 Windows 识别。

**前置：**§3 编译方法，§6.1～§6.3。文件：`make_wav.cpp`。

```cpp
#include <cmath>
#include <cstdint>
#include <fstream>
#include <iostream>

// WAV integer fields in this example use little-endian byte order.
void write16(std::ostream& out, std::uint16_t value) {
    out.put(static_cast<char>(value & 0xff));
    out.put(static_cast<char>((value >> 8) & 0xff));
}

void write32(std::ostream& out, std::uint32_t value) {
    for (int shift = 0; shift < 32; shift += 8) {
        out.put(static_cast<char>((value >> shift) & 0xff));
    }
}

int main() {
    constexpr std::uint32_t sampleRate = 48000;
    constexpr std::uint16_t channels = 1;
    constexpr std::uint16_t bits = 16;
    constexpr std::uint32_t seconds = 2;
    constexpr std::uint16_t blockAlign = channels * bits / 8;
    constexpr std::uint32_t sampleFrames = sampleRate * seconds;
    constexpr std::uint32_t dataBytes = sampleFrames * blockAlign;
    constexpr double pi = 3.14159265358979323846;
    constexpr double frequency = 440.0;
    constexpr double amplitude = 0.25; // Keep sample values below clipping.

    std::ofstream file("tone.wav", std::ios::binary);
    if (!file) {
        std::cerr << "Cannot open tone.wav\n";
        return 1;
    }
    file.write("RIFF", 4);
    write32(file, 36 + dataBytes);
    file.write("WAVE", 4);
    file.write("fmt ", 4);
    write32(file, 16);                  // PCM format chunk size.
    write16(file, 1);                   // 1 means integer PCM.
    write16(file, channels);
    write32(file, sampleRate);
    write32(file, sampleRate * blockAlign);
    write16(file, blockAlign);
    write16(file, bits);
    file.write("data", 4);
    write32(file, dataBytes);

    for (std::uint32_t i = 0; i < sampleFrames; ++i) {
        const double t = static_cast<double>(i) / sampleRate;
        const auto sample = static_cast<std::int16_t>(std::lround(
            amplitude * 32767.0 * std::sin(2.0 * pi * frequency * t)));
        write16(file, static_cast<std::uint16_t>(sample));
    }
    file.close();
    if (!file) {
        std::cerr << "Write failed\n";
        return 1;
    }
    std::cout << "Wrote tone.wav, PCM bytes: " << dataBytes << '\n';
}
```

几个关键点：

1. `sin(...)` 生成周期性波形；`i/sampleRate` 给出第 i 个采样时刻。
2. `amplitude` 是音量相关的幅度比例。超出可表示范围会出现**削波 clipping**，波形被切平并产生失真；不要通过强转溢出来调音量。
3. WAV 小端字段是低位字节在前。例如 16 位数 `0x1234` 写成 `34 12`。网络协议中则常见大端，必须分别遵守格式。
4. 本例只有单声道，所以每次循环写一个样本；改双声道时要在每个采样时刻写左右两个样本，同时更新头字段。
5. 本例使用最简单的 44 Byte PCM WAV 文件头，不覆盖所有 WAV 变种或超大文件格式。

按 §3 编译运行 `make_wav.cpp`。预期 `PCM bytes: 192000`，文件总大小 192,044 Byte，时长 2 秒。

## 7. 视频压缩：为什么不是每帧都能独立解码

### 7.1 编码格式、编码器与压缩手段

**前置：**§4 的原始视频数据量、§5 的像素表示。

原始视频很大，编码器会寻找可压缩的信息。可以先理解两类办法：

- **帧内压缩**：在同一张图内部找相似区域，减少重复信息。
- **帧间压缩**：利用相邻图像的相似性，用预测和差异信息表达新图像。

实际编码还包括变换、量化、熵编码等步骤。此时不必推导数学过程，但要明白压缩流不是简单的“原图或像素相减文件”。

**编码格式/标准**规定压缩数据如何解释，例如 H.264/AVC、H.265/HEVC、AAC、Opus。**编码器**是生成该格式的软件或硬件实现，例如 `libx264` 产生 H.264，`libx265` 产生 H.265。不同实现可以产生同一种编码格式，速度与画质也可能不同。

**解码器**则按格式规则还原图像或声音。H.264 解码器不能直接解码 H.265；更换扩展名也不会改变数据格式。

H.265 在许多应用中有更好的压缩效率，但收益随内容、编码器和参数变化，不能保证固定省一半；兼容性、设备支持和计算成本也要考虑。先掌握 H.264 路径，再比较 H.265。

**Profile（档次）**限制所用编码工具，**Level（级别）**约束尺寸、处理速率等能力范围。设备宣称支持“H.264”不等于支持全部档次、位深、色度格式和分辨率组合。

**常见错误：**把 `libx264` 当容器；认为只要码率加大就能恢复输入中本来不存在的细节；反复有损转码后期望画质不变。

### 7.2 I、P、B：按什么信息进行预测

**前置：**帧内与帧间压缩。

先用简化的“整张图像”模型理解：

| 类型 | 初学者理解 | 需要注意 |
|---|---|---|
| I 图像 | 主要使用图像内部的信息 | 不意味着一定是可清空所有历史依赖的随机访问点 |
| P 图像 | 可使用参考图像来预测 | 丢失参考可能影响后面的图像 |
| B 图像 | 可使用两个参考列表进行预测，常见为前后图像 | 不应简单等同于“绝不被其他图像参考” |

严格来说，H.264 中 I/P/B 也是 slice（条带，图像中的编码区域）的类型；一张图像可能含多个 slice。这里的整帧说法是建立直觉用的简化模型。

所谓“未来参考”，指的是**显示顺序上的未来**。解码器得先拿到参考信息，因此解码顺序可能与显示顺序不同，§9 的 PTS/DTS 正是为此服务。

**常见错误：**认为每个压缩包独立丢弃都没关系。若丢的是后续图像所依赖的参考，可能出现花屏、错误传播，直到合适的恢复点。

### 7.3 IDR、关键帧、GOP 与首次出画

**前置：**I/P/B 与参考依赖。

**IDR（即时解码刷新图像）**是 H.264 中一种明确的随机访问/刷新点：后续图像不会再依赖 IDR 之前的图像。新客户端如果从可用的参数集和合适的 IDR 开始，便更容易建立正确解码状态。

**关键帧 keyframe**是工具和容器里常见的标记，表示用于访问或恢复的关键位置。不要把所有标为 I 的图像、所有库里的 key 标记都不加区分地当作 IDR；具体语义随编码与接口而定。H.265 还有 IDR、CRA 等不同随机访问类型，后续再细学。

**GOP（Group of Pictures，图像组）**常用来描述一段图像的预测组织。实践中也会用“GOP 长度/关键帧间隔”粗略表示多少帧出现一次关键位置；开放 GOP 与封闭 GOP 的依赖边界并不相同，不能仅从一个间隔数字推断全部依赖。

入门可先使用 30 fps、每 60 帧一个 IDR 的封闭、简单结构模型：

```text
IDR P P P ... 共 60 帧 ... IDR P P P ...
两个 IDR 的显示时间间隔约为 60 / 30 = 2 秒
```

若随机加入且确实必须等下一个周期性 IDR，理想等待范围约为 0～2 秒，平均约 1 秒；网络、参数集与解码缓冲还会增加等待。实际还可以缓存最近的可用关键序列、请求关键帧或调整编码器。

关键帧间隔短通常更利于快速加入和丢包后恢复，但常增加码率或在相同码率下降低画质。关键帧间隔长不代表播放过程中必然固定多等一个完整 GOP；首次出画等待、B 帧重排和稳定播放延迟是不同来源。

**练习：**25 fps、每 50 帧出现一个可用 IDR，理想首次等待上限约多少？如果每帧原本可独立解码，丢一帧与丢一个参考 P 帧有什么不同？

### 7.4 低延迟编码与解码边界

**前置：**GOP 与 B 帧。

为直播低延迟，常会减少 B 帧重排、减少编码器前向分析（lookahead）、控制内部缓存，并选择合适关键帧间隔。代价可能是压缩效率或画质下降；“低延迟”不是无成本的开关。

画面不更新也不一定是网络没数据：可能在等参数集、等可用关键帧、等未来参考，也可能显示队列还没到播放时间。排查时要分别记录接收、解包、解码输出和显示的数量与时间。

**阶段检查：**

- [ ] 我能说明编码标准与编码器实现的区别。
- [ ] 我知道预测帧可能依赖其他图像，不能随意丢压缩数据。
- [ ] 我知道普通 I 图像不应一概等同于 IDR。
- [ ] 我会把关键帧间隔从帧数换算为秒。
- [ ] 我能分别解释首次出画等待和持续播放延迟。

## 8. 编码、封装与 NAL：先给每层数据分好工

### 8.1 容器、裸流与网络协议

**前置：**§2 的处理链、§7 的编码格式。

**容器/封装格式**像文件夹，装入视频、音频以及时间戳、索引、元数据。例如 MP4、Matroska（常见 `.mkv`）、MPEG-TS。**编码格式**则规定文件夹里的媒体压缩数据如何解释。

```text
MP4 容器
├─ 视频轨道：H.264 压缩数据 + 时间信息
├─ 音频轨道：AAC 压缩数据 + 时间信息
└─ 描述信息、索引等
```

**流 stream/轨道 track**表示其中一条媒体序列；文件中可能有多个音轨、多个视频流和字幕流。**解封装 demux**是从容器里分离各路压缩数据及相关信息；**解码 decode**才是将压缩数据还原成像素或样本。反方向分别是封装 mux 与编码 encode。

**裸流/基本码流**指没有 MP4 这类外层容器的编码数据，例如 Annex B 形式的 `.h264`。裸流可能包含一些编码参数，但通常缺少容器中完整的时间戳、索引、音画对应信息。原始 `.yuv`、PCM 更是未压缩数据，不能和 H.264 裸压缩流混为一谈。

| 名称 | 所在层次 | 典型职责 |
|---|---|---|
| RGB24、YUV420P、PCM s16le | 原始表示 | 怎样保存像素或采样值 |
| H.264、H.265、AAC、Opus | 编码 | 怎样压缩与解压媒体 |
| MP4、MKV、MPEG-TS、WAV | 容器 | 怎样组合媒体与描述信息 |
| RTP | 媒体传输 | 提供包序号、媒体时间戳等；载荷结构另有规范 |
| RTSP | 会话控制 | 协商、开始、暂停、结束等控制 |
| UDP、TCP | 传输层 | 在端点之间传送数据 |

**重新封装 remux**只改变外层组织，通常不重新编码。例如 FFmpeg 的 `-c copy`；**转码 transcode**通常涉及解码再编码。前者通常更快且不会引入一轮有损编码，但新容器必须支持原有编码，码流表示也可能需要相应转换。

**常见错误：**把 `.mp4` 改名成 `.h264` 当成格式转换；将 demux 得到的 H.264 包直接按 RGB 使用；认为容器格式决定清晰度。

**练习：**将“MP4、H.264、AAC、RGB24、RTP、RTSP、TCP”分别归类，并写出一条从文件到画面的处理链。

### 8.2 H.264 的 NAL、SPS、PPS 与访问单元

**前置：**H.264 是编码格式，压缩图像可能依赖其他图像。

**NAL Unit（网络抽象层单元）**是 H.264 码流的一种组织单元。可以先当作“带一个小头部的编码内容块”。对于常见 H.264 NAL，第一个字节是头部：

```text
bit 7          bit 6..5       bit 4..0
forbidden_bit  nal_ref_idc    nal_unit_type
常规应为 0     参考相关信息   低 5 位表示类型
```

即 `type = header & 0x1f`。H.265 NAL 头的结构不同，不能套用这个规则。

| H.264 NAL 类型 | 名称 | 初学含义 |
|---|---|---|
| 1 | non-IDR slice | 非 IDR 图像的编码条带；仅凭类型 1 不能判断 I/P/B |
| 5 | IDR slice | IDR 图像的编码条带 |
| 6 | SEI | 补充信息，具体内容需进一步解析 |
| 7 | SPS，序列参数集 | 分辨率、档次等解码配置的一部分 |
| 8 | PPS，图像参数集 | 条带解码需要的另一组配置 |
| 9 | AUD，访问单元分隔符 | 可用于提示边界，但并非所有流都有 |

**Slice**可以理解为一张图像里的一个编码区域。一个视频图像可能有多个 slice NAL。**访问单元 Access Unit，简称 AU**是对应一个编码图像的相关 NAL 集合，可能还包含非图像数据。它不等于“任意一个 NAL”。

解码器往往需要正确的 SPS/PPS 和可用参考状态才能出画。SPS/PPS 可能在码流内，也可能通过容器的额外数据或 SDP 带外提供；中途分辨率变化还可能伴随参数集更新。不能把拿到的第一组参数永远写死。

**常见错误：**把每个 NAL 都当作独立视频帧；只收 IDR slice 却缺 SPS/PPS；把 NAL type 1 一律叫 P 帧。

### 8.3 Annex B 与 AVCC：如何知道一个 NAL 到哪里结束

**前置：**字节数组、NAL 头部。

NAL 要放进字节流，读者必须识别边界。H.264 常见两种外层表示：

**Annex B**：使用起始码分隔 NAL，常见起始码为 `00 00 01` 或 `00 00 00 01`。

```text
00 00 00 01 | 67 ... SPS ... | 00 00 01 | 68 ... PPS ... |
00 00 01 | 65 ... IDR slice ... |
```

**长度前缀形式**：每个 NAL 前放长度；经常在 MP4/AVC 的上下文中被称为 AVCC 形式。长度字段宽度由 `AVCDecoderConfigurationRecord`（常见盒子名 `avcC`）的配置决定，常见 4 Byte，不能在所有输入中硬编码为 4。长度通常按大端表示，值不包含长度字段本身。

```text
假设配置指定 4 字节长度：
00 00 00 04 | 67 42 00 1E | 00 00 00 03 | 68 CE 06 |
长度是 4       4 字节 NAL    长度是 3       3 字节 NAL
```

上面只是边界示意，不是完整可解码视频。Annex B 与长度前缀都是组织相同类型 NAL 的方式，转换边界不等于重新编码。

NAL 负载中会使用**防竞争字节/防起始码仿真字节**来避免伪装成起始码的序列。这里只需知道：不能对所有媒体包任意搜索 `00 00 01`，也不能随意删除全部 `03` 字节。解析 NAL 内容还需要遵循规范。

RTP 中的 H.264 载荷通常按 RFC 6184 打包，可能是单 NAL、聚合或分片；不会自动带有 Annex B 起始码。应先完成 RTP/H.264 解包，再按解码器要求形成输入。细节见 [[07-H264与RTP封装]]。

### 8.4 实验五：扫描教学字节中的 NAL 类型

**目标：**认识边界和头部。文件：`annexb_scan.cpp`。本例只扫描内存中固定的**教学数据**，不是通用码流解析器，数据也不能播放。

```cpp
#include <cstddef>
#include <cstdint>
#include <iostream>
#include <vector>

std::size_t prefixLength(const std::vector<std::uint8_t>& bytes,
                         std::size_t pos) {
    if (pos + 4 <= bytes.size() && bytes[pos] == 0 && bytes[pos + 1] == 0 &&
        bytes[pos + 2] == 0 && bytes[pos + 3] == 1) {
        return 4;
    }
    if (pos + 3 <= bytes.size() && bytes[pos] == 0 && bytes[pos + 1] == 0 &&
        bytes[pos + 2] == 1) {
        return 3;
    }
    return 0;
}

int main() {
    const std::vector<std::uint8_t> bytes = {
        0, 0, 0, 1, 0x67, 0x42, 0x00, 0x1e,
        0, 0, 1, 0x68, 0xce, 0x06,
        0, 0, 1, 0x65, 0x88, 0x84,
        0, 0, 1, 0x41, 0x9a, 0x22
    };
    std::size_t pos = 0;
    while (pos < bytes.size()) {
        const auto prefix = prefixLength(bytes, pos);
        if (prefix == 0) {
            ++pos;
            continue;
        }
        const auto begin = pos + prefix;
        if (begin == bytes.size()) {
            std::cerr << "Start code without a NAL header\n";
            return 1;
        }
        auto end = begin;
        while (end < bytes.size() && prefixLength(bytes, end) == 0) {
            ++end;
        }
        const auto header = bytes[begin];
        if ((header & 0x80) != 0) {
            std::cerr << "Invalid forbidden_zero_bit\n";
            return 1;
        }
        std::cout << "offset=" << pos
                  << " prefix=" << prefix
                  << " type=" << static_cast<unsigned>(header & 0x1f)
                  << " nal_bytes=" << end - begin << '\n';
        pos = end;
    }
}
```

按 §3 编译运行，预期输出：

```text
offset=0 prefix=4 type=7 nal_bytes=4
offset=8 prefix=3 type=8 nal_bytes=3
offset=14 prefix=3 type=5 nal_bytes=3
offset=20 prefix=3 type=1 nal_bytes=3
```

真实解析器还要处理输入跨块、前导/尾随零字节、合法语法、访问单元边界和错误数据等。不能直接把这个教学扫描器粘进网络线程当作生产解包器。

**练习：**将最后一个头字节 `0x41` 改成 `0x65`，预测输出；在末尾追加 `0,0,1`，确认程序会报告缺少 NAL 头。解释为什么扫描出的 4 个 NAL 不能直接称为 4 帧。

- [ ] 我能区分容器、编码、原始表示和网络协议。
- [ ] 我能解释 remux 与 transcode。
- [ ] 我知道 SPS/PPS、IDR、slice、AU 分别解决什么问题。

## 9. 时间体系：每个数字到底在用哪把尺子

### 9.1 时间戳、时间基与时钟频率

**前置：**帧率、采样率、分数、整数除法。

**时间戳 timestamp**是一个表示时间位置的数字。但单独给你 `90000` 并无意义：它可能是 90 秒、1 秒或别的时长，取决于单位。

**时间基 time base**就是“一个刻度有多长”，常写成分数 `num/den` 秒：

```text
时间（秒）= 时间戳 × num / den
若 time_base = 1/90000，90000 个刻度就是 1 秒
若 time_base = 1/48000，1024 个刻度约为 21.333 毫秒
若 time_base = 1001/30000，30 个刻度就是 1.001 秒
```

**时钟频率 clock rate**表示一秒有多少刻度。如果频率为 F Hz，相应时间基通常是 `1/F` 秒。时钟频率不是 CPU 主频，也不是视频帧率。

使用整数刻度与有理数，可以避免长时间累计浮点误差，也能精确表示 `30000/1001` 等速率。不要每帧都把 33.366... ms 截成 33 ms 再累加，应从原始时间戳进行换算。

**常见错误：**拿一个流的 PTS 数字直接与另一个不同时间基的 PTS 比较；把媒体中的时间位置误认成电脑当前日期时间。

### 9.2 PTS 与 DTS：显示顺序可能不同于解码顺序

**前置：**§7 的 B 帧与参考依赖。

- **PTS，Presentation Time Stamp**：这份媒体应该在时间轴的什么位置呈现，即什么时候显示或播放。
- **DTS，Decoding Time Stamp**：对应解码顺序的时间位置，表示何时进入解码处理时间线；不要把它当作实际测出来的 CPU 开始工作时间。

没有重排的简单流，PTS 与 DTS 可能相同；有 B 帧的流则可能不同。例如显示顺序是 `I0 B1 B2 P3`，B1/B2 需要 P3 做参考，因此送入解码器的顺序可以是 `I0 P3 B1 B2`。

下面是**人为构造的 25 fps 教学时间线**，为方便演示，把 PTS 整体加了 80 ms；不代表所有文件都有这个偏移：

| 送入解码器的顺序 | 图像 | DTS（ms） | PTS（ms） |
|---|---|---:|---:|
| 1 | I0 | 0 | 80 |
| 2 | P3 | 40 | 200 |
| 3 | B1 | 80 | 120 |
| 4 | B2 | 120 | 160 |

解码器输入按 DTS/正确码流顺序处理，显示按 PTS 时间呈现。真实文件还可能使用负 DTS、非零起始时间或缺失时间戳，库也可能为输出帧提供估算后的时间戳。

**常见错误：**先按 PTS 对压缩包排序，再送入解码器，这会破坏参考依赖；或者按网络到达顺序立即显示，导致重排和抖动问题。

**练习：**按 PTS 从小到大排列上表的图像，并解释为什么 P3 必须较早解码。

### 9.3 RTP Timestamp、序号与回绕

**前置：**时间基、媒体帧、32 位整数。

RTP 头部有两种不同计数：

- **sequence number（序号）**：通常每发一个 RTP 包加 1，用来辅助发现丢包和重排；是 16 位，会回绕。
- **timestamp（时间戳）**：描述该载荷对应的媒体采样时间；是 32 位，不是每个包机械加 1。

H.264 over RTP 使用 90,000 Hz 媒体时钟。因此在理想 30 fps 下，相邻图像的 RTP 时间戳差可为 `90000/30 = 3000`。一张图像拆成多个 RTP 包时，这些包通常共享同一个图像时间戳，序号则逐包变化。

`30000/1001` fps 在 90 kHz 下每帧是 3003 个刻度。其他不能整除的帧率可能需要交替的时间戳增量，不能强行把所有情况写死为 3000。

音频的 RTP 时钟取决于载荷格式和 SDP 的协商。例如 Opus RTP 按规范使用 48 kHz 时钟，即使内部音频来源使用别的采样率。必须读媒体描述，不能把所有音频时钟也当成 90 kHz。

RTP 初始时间戳通常具有随机偏移，音频和视频可以有不同起点。直接比较 `audio_rtp_ts` 与 `video_rtp_ts` 大小没有意义。要换算各自相对时间，并通过已知对应关系对齐；RTCP Sender Report 提供 RTP 时间戳与 NTP 时间的映射，后续见 [[06-RTCP协议]]。

32 位计数走到最大值后会从 0 继续，即**回绕**。90 kHz 的完整周期约 `2^32/90000 ≈ 13.26 小时`。对于已知向前、跨度较小的一段，可以使用无符号减法计算跨回绕增量；真实接收器还必须区分乱序、旧包、流重启、SSRC 切换和回绕，不能把每次变小都判作回绕。

### 9.4 实验六：时间戳换算与回绕

**目标：**把“刻度”换成“毫秒”，观察跨回绕的局部差值。文件：`clock_math.cpp`。

```cpp
#include <cstdint>
#include <iostream>
#include <limits>
#include <stdexcept>

// Teaching helper: non-negative timestamps, positive rational time base.
// Returns integer milliseconds, truncating the fractional remainder.
std::int64_t toMilliseconds(std::int64_t ticks,
                            std::int64_t num, std::int64_t den) {
    if (ticks < 0 || num <= 0 || den <= 0) {
        throw std::invalid_argument("Invalid teaching input");
    }
    const auto maxValue = std::numeric_limits<std::int64_t>::max();
    if (ticks > maxValue / num / 1000) {
        throw std::overflow_error("Intermediate multiplication is too large");
    }
    return ticks * num * 1000 / den;
}

int main() {
    std::cout << "90000 @ 1/90000, ms: "
              << toMilliseconds(90000, 1, 90000) << '\n';
    std::cout << "3000 @ 1/90000, truncated ms: "
              << toMilliseconds(3000, 1, 90000) << '\n';
    std::cout << "1024 @ 1/48000, truncated ms: "
              << toMilliseconds(1024, 1, 48000) << '\n';
    std::cout << "30 @ 1001/30000, ms: "
              << toMilliseconds(30, 1001, 30000) << '\n';

    const std::uint32_t before = 0xfffffff0u;
    const std::uint32_t after = 0x00000020u;
    const std::uint32_t delta = after - before;
    std::cout << "RTP forward wrap delta: " << delta << '\n';
    std::cout << "RTP delta, ms: " << delta * 1000.0 / 90000.0 << '\n';
}
```

按 §3 编译运行，预期依次为 `1000`、`33`、`21`、`1001`、`48`、约 `0.533333`。本例整数毫秒有意截断，仅展示单位换算；真实调度应保留更高精度，不能把截断值逐次累加。

这不是通用时间库：不支持负时间戳或缺失值，也不通过约分处理所有中间乘法溢出。FFmpeg 开发中常用 `av_rescale_q` / `av_rescale_q_rnd` 在有理时间基之间换算，并处理 `AV_NOPTS_VALUE` 等缺失标记；具体接口留到 [[08-FFmpeg与解码]]。

**练习：**计算 180,000 个 90 kHz 刻度对应几秒；计算 960 个 48 kHz 刻度对应几毫秒；解释为什么循环相加 33 ms 会比 30 fps 的真实时间线跑快。

## 10. 音视频同步：让嘴型和声音对上

### 10.1 先建立共同时间轴

**前置：**§9 的时间基、PTS 和时钟起点。

同步不是“同时收到就同时播放”。网络到达时刻带有传输抖动；解码完成时刻还受 CPU 负载影响。播放应参照媒体时间线。

假设同一事件对应视频 PTS `90000`、时间基 `1/90000`，音频 PTS `48000`、时间基 `1/48000`，两者都在第 1 秒，但数字不同。若起点也不同，先要建立起点的对应关系，不能只各自减首个包就假定它们同步。

文件通常通过容器的时间信息对齐；RTP 会话可能通过 RTCP 的时钟映射和流关联信息对齐。没有可靠共同参照时，仅凭到包时间只能做近似估计。

### 10.2 以音频为主时钟的一种常见方案

**前置：**PCM 样本数、PTS。

音频对连续性敏感：随便丢一段容易出现跳音或爆音。许多播放器以**已经实际播放的音频位置**作为主时钟，让视频跟随它。

音频时钟的近似关系是：

```text
音频已播放时间 ≈ 起始媒体时间 + 已交给设备的样本帧数 / 采样率 − 设备中尚未播放的缓存时长
```

只统计“交给声卡的数据量”会把还在缓冲里的声音也算作已播放，导致画面跑在声音前面。真实实现应读取音频设备的播放位置或估计其缓存延迟。

一帧视频的 PTS 换成同一时间单位和起点后，与音频时钟比较：

- 视频还早：等待到合适时刻再显示。
- 视频略晚：尽快显示，允许小范围误差。
- 视频严重落后：直播场景可丢掉部分已经解码、尚未显示的旧帧来追赶。

“等待/丢弃”的阈值必须根据帧间隔、内容与产品目标设定；没有适用于全部播放器的固定值。

### 10.3 实验七：用 C++ 模拟同步决策

**目标：**区分解码与呈现，不需要声卡或窗口库。文件：`sync_policy.cpp`。

```cpp
#include <cstdint>
#include <iostream>

int main() {
    // All values are milliseconds on the SAME already-aligned timeline.
    const std::int64_t audioClockMs = 1000;
    const std::int64_t maxLateMs = 80; // Teaching policy, not a standard.
    const std::int64_t decodedVideoPts[] = {880, 970, 1000, 1040};

    for (const auto pts : decodedVideoPts) {
        const auto diff = pts - audioClockMs;
        std::cout << "video=" << pts << " diff=" << diff << " -> ";
        if (diff < -maxLateMs) {
            std::cout << "drop decoded frame\n";
        } else if (diff > 0) {
            std::cout << "wait " << diff << " ms\n";
        } else {
            std::cout << "show now\n";
        }
    }
    std::cout << "10 queued frames at 30 fps add about "
              << 10 * 1000.0 / 30 << " ms of media backlog\n";
}
```

按 §3 编译运行，前四项应分别是：丢弃、立即显示、立即显示、等待 40 ms；队列积压约 333.333 ms。这里只有决策输出，没有真的等待或显示；实际播放时主时钟持续前进，等待结束后还要重新比较。

**重要边界：**这里丢弃的是**已解码的旧视频帧**，不随意跳过解码器依赖的压缩参考帧。直播严重积压时，若要在压缩层跳转，通常需要按正确的随机访问/恢复策略重建状态。

### 10.4 同步误差、长期漂移和本地时钟

**前置：**掌握同一时间轴上的比较。

如果开始时声画有固定 200 ms 偏差，优先检查起点对齐与设备缓冲。如果开始对齐、几分钟后逐渐偏离，则可能是两个时钟速度不同、帧率用错、累计取整或音频采样率不匹配，称为**时钟漂移 drift**。

真实系统可能通过微调音频重采样比例、调整视频呈现策略等方式修正漂移，不是周期性粗暴清空所有队列。

本地等待与测量时间间隔可使用 `std::chrono::steady_clock`，因为它不会被手动校时直接跳变。`system_clock` 适合表示墙上日期时间，可能被校时调整。不要把来自这两个时钟的时间点直接相减，也不要把 `steady_clock` 的计数当作 RTP 或 PTS。

没有音轨时，可以把首帧的媒体时间映射到某个 `steady_clock` 起点，再按媒体时间差调度视频；仍要保留真实 PTS 间隔。

**常见错误：**按收包速度播放；每帧固定睡 33 ms、再加上处理耗时，导致越来越慢；忽略声卡缓存；把不同时间基、不同起点或不同本地时钟混算。

**练习：**音频时间为 2,000 ms，视频 PTS 为 2,040 ms 和 1,700 ms，各应如何处理？若视频延迟每分钟增加 60 ms，应优先怀疑固定起点偏差还是时钟速度偏差？

**阶段检查：**

- [ ] 我能先统一时间基和起点，再比较音画时间。
- [ ] 我知道音频“已提交”和“已播放”的区别。
- [ ] 我能解释本节同步模拟器做了什么、没有实现什么。

## 11. 延迟与缓冲：为什么流畅和实时并不总一致

### 11.1 端到端延迟由哪些部分组成

**前置：**编码、解码、队列、同步时钟。

**端到端延迟**指现实事件发生，到接收端呈现该事件之间经过的时间。视频看起来不卡，不等于延迟小；播放器可能一直在顺畅播放两秒前的画面。

用一个仅为计算练习的预算举例：

| 环节 | 示例耗时 | 为什么会等待 |
|---|---:|---|
| 采集/凑帧 | 33 ms | 摄像头形成一帧需要时间 |
| 编码与前向分析 | 20 ms | 编码计算或等待后续图像 |
| 网络 | 15 ms | 传播、排队、传输 |
| 抖动缓冲 | 60 ms | 等可能迟到或乱序的数据 |
| 解码与重排 | 20 ms | 计算或等待参考图像 |
| 显示/音频设备缓存 | 30 ms | 呈现排队、设备缓冲 |
| 合计 | 178 ms | 只代表这组假设数字 |

实际环节可能并行，测量边界也可能重叠，所以最终以端到端实测为准，不能机械相加所有日志耗时。先明确每个时间点记录的含义。

### 11.2 抖动、队列、背压与丢帧

**前置：**数据到达顺序与呈现时间不同。

网络延迟的变化叫**抖动 jitter**。抖动缓冲会保留少量数据，给晚到和乱序数据一个等待窗口。缓冲过小可能卡顿，过大又增加延迟。

**队列**是保存待处理数据的容器。例如每秒来 30 帧，却只能处理 25 帧，每秒净积压 5 帧。持续 10 秒会积压约 50 帧，相当于约 1.67 秒媒体时间；无限队列最终会同时吃掉内存和实时性。

**背压 backpressure**表示下游处理不过来时，向上游反馈或限制继续积压。直播系统常使用有界队列，并按数据层次选择策略：

- 网络包/压缩层：要考虑帧完整性、参考依赖、重传价值与恢复点，不能简单“每隔几个字节丢一次”。
- 解码后的视频帧：可以按播放时间丢旧画面，优先追上实时。
- 音频样本：需要保持连续，并以音频播放策略、重采样或受控跳转处理，不能任意删除几个字节。

队列长度最好同时限制帧数、字节数和媒体时长。1920×1080 的紧密 YUV420P 一帧约 3.11 MB，缓存 100 帧仅像素就约 311 MB，还没计入解码器参考帧和其他结构。

### 11.3 TCP 与 UDP 对媒体有什么影响

**前置：**知道它们是传输协议；协议实现见 [[01-网络与Socket基础]]。

TCP 提供可靠、有序字节流。丢失的一段重传完成前，后面的字节可能暂时不能交给上层，直播表现为等待和延迟增加。它不保留应用消息边界，仍需按 RTSP/RTP 规则解析。

UDP 不保证交付或顺序。应用要处理丢失、乱序和过期数据，但也有机会直接舍弃迟到数据继续追实时。实际效果受网络、防火墙、编码结构、恢复机制影响；不能简单说 UDP 必然更快或 TCP 必然不适合直播。

**常见错误：**延迟增大就盲目加缓存；只看平均 CPU 占用，不检查单线程处理瓶颈；在压缩层乱丢参考数据；把首次等待关键帧误当作网络传输延迟。

### 11.4 如何实际测量

**前置：**§10 的本地时钟。

1. 端到端直观测量：让摄像头拍摄持续变化的计时器，同时拍下现场计时器与接收端画面，比较两者数值。刷新粒度、滚动快门等会影响精度，重复测量并给出范围。
2. 客户端内部测量：用同一个 `steady_clock` 记录完整数据到达、解包完成、解码输出、呈现的时刻，观察各段耗时和队列积压。
3. 跨机器测量：两个机器的本地单调时钟起点不同，不能直接相减；需要同步时钟或专门建立时钟映射，还应记录同步误差。
4. 不要只报告“缓存 10 帧”；应同时写出帧率或时间跨度，并分别记录音视频。

**练习：**一个 30 fps 的实时源，处理速度长期为 28 fps，15 秒后理论上积压多少帧、相当于多少秒？限制队列后应该如何处理旧视频，以及为什么不能在任意层直接丢？

### 12.2 生成统一的音视频素材

**目标：**不用摄像头、服务器或网络，先获得所有人都能重新生成的媒体。

```powershell
ffmpeg -n -f lavfi -i "testsrc2=size=640x360:rate=30" -f lavfi -i "sine=frequency=440:sample_rate=48000" -t 6 -c:v libx264 -pix_fmt yuv420p -g 60 -bf 2 -crf 23 -c:a aac -b:a 128k -movflags +faststart .\sample.mp4
if ($LASTEXITCODE -ne 0) { throw 'FFmpeg failed' }
ffplay -autoexit -i .\sample.mp4
```

参数逐个读：

- `-f lavfi`：输入来自 FFmpeg 的滤镜生成器，不是真实文件。
- `testsrc2`：生成会变化的测试画面；`size` 是尺寸，`rate` 是帧率。
- `sine`：生成正弦声音；输入默认是单声道。
- `-t 6`：输出约 6 秒。
- `-c:v libx264` / `-c:a aac`：分别指定视频、音频编码器。
- `-pix_fmt yuv420p`：指定视频像素格式。
- `-g 60`：设置最大关键帧间隔；场景切换等机制可能导致更早的关键帧，不应简单当作保证每 60 帧整齐出现一次。
- `-bf 2`：允许最多连续 2 个 B 帧；具体结果由编码器决定。
- `-crf 23`：此编码器的质量控制参数，不是 23 Mb/s。
- `-b:a 128k`：音频目标码率约 128 kb/s。
- `-movflags +faststart`：调整 MP4 元数据位置，便于普通文件渐进式读取；它不是 RTSP 低延迟开关。

预期：出现活动测试图，并听到持续音调。它适合观察格式，**不适合验证嘴型同步**；验证同步需要明确同时发生的画面闪烁/拍手与声音脉冲等事件。

### 12.3 查看媒体信息，先写判断再播放


字段解释：

| 字段 | 怎样读 |
|---|---|
| `codec_name` | 流使用的编码，如 h264、aac |
| `format_name` | 容器探测名称，可能是一组相关格式名 |
| `pix_fmt` | 像素布局与精度，不是编码名称 |
| `time_base` | 时间戳的单位；MP4 视频不保证等于 1/90000 |
| `r_frame_rate` / `avg_frame_rate` | 需结合时间戳理解；尤其 VFR 时不能只看一个数字推断帧间隔 |
| `stream.bit_rate` | 该条流的码率信息，可能缺失或只是估计 |
| `format.bit_rate` | 整个文件的平均总码率，包含音频和封装等 |
| `color_*` | 色彩描述；缺失不等于证明某个默认解释正确 |

**练习：**先不用播放器，写出文件中有几条流、每条流是什么；根据文件大小与时长估算总码率，再与探测值比较。

### 12.4 观察压缩包和解码帧的时间

先看视频压缩包：

```powershell
ffprobe -v error -select_streams v:0 -read_intervals "%+#12" -show_packets -show_entries "packet=pts,pts_time,dts,dts_time,duration_time,size,flags" -of compact .\sample.mp4
```

`v:0` 选择第一条视频流；`%+#12` 从起始处读取约 12 个包进行观察；`*_time` 是换算为秒的结果。允许 B 帧的素材常会看到 PTS 与 DTS 不同，首个 DTS 也可能为负数；这并不自动表示损坏。`flags` 中的关键标记属于接口层语义，不替代完整码流分析。

再看解码后的图像帧：

```powershell
ffprobe -v error -select_streams v:0 -read_intervals "%+#12" -show_frames -show_entries "frame=pts_time,best_effort_timestamp_time,pict_type,key_frame" -of compact .\sample.mp4
```

输入包数和输出帧数不必在这个短窗口内一一对应：解码器存在缓冲、重排和刷新过程。观察 `pict_type` 的 I/P/B、输出帧的呈现时间；具体帧型排列取决于编码器。

音频包同样可以观察：

```powershell
ffprobe -v error -select_streams a:0 -read_intervals "%+#8" -show_packets -show_entries "packet=pts,pts_time,duration,duration_time,size" -of compact .\sample.mp4
```

在这组常见 AAC-LC 配置下，通常可看到约 21.333 ms 的包时长。留意开头的编码延迟信息和结尾填充，别把所有音频包都当成一段严格无例外的固定数据。

**常见错误：**只看 `pts` 的整数，不看 `time_base`；把负 DTS 当异常；把 `-show_packets` 与 `-show_frames` 的结果当成同一对象。

### 12.5 同时比较分辨率与目标码率

**目标：**控制变量。每个输出使用同样的 6 秒源画面，分别组合两种分辨率和两种视频目标码率，不含音轨。

```powershell
ffmpeg -n -f lavfi -i "testsrc2=size=1280x720:rate=30" -t 6 -an -vf "scale=640:360" -c:v libx264 -pix_fmt yuv420p -b:v 300k .\360p_300k.mp4
ffmpeg -n -f lavfi -i "testsrc2=size=1280x720:rate=30" -t 6 -an -vf "scale=640:360" -c:v libx264 -pix_fmt yuv420p -b:v 1200k .\360p_1200k.mp4
ffmpeg -n -f lavfi -i "testsrc2=size=1280x720:rate=30" -t 6 -an -vf "scale=1280:720" -c:v libx264 -pix_fmt yuv420p -b:v 300k .\720p_300k.mp4
ffmpeg -n -f lavfi -i "testsrc2=size=1280x720:rate=30" -t 6 -an -vf "scale=1280:720" -c:v libx264 -pix_fmt yuv420p -b:v 1200k .\720p_1200k.mp4
```

每条结束后检查 `$LASTEXITCODE`；`-an` 表示不输出音频。`-b:v` 是目标平均码率控制，不保证 6 秒短片严格达到该值，也不等于设置了严格 CBR。

```powershell
Get-ChildItem .\360p_*.mp4,.\720p_*.mp4 | Select-Object Name,Length

```

对其他三个文件重复探测和播放，填写：

| 文件 | 实际大小 | 实际总码率 | 同样窗口大小下的文字/边缘/运动效果 |
|---|---|---|---|
| 360p_300k.mp4 | 待测 | 待测 | 待观察 |
| 360p_1200k.mp4 | 待测 | 待测 | 待观察 |
| 720p_300k.mp4 | 待测 | 待测 | 待观察 |
| 720p_1200k.mp4 | 待测 | 待测 | 待观察 |

### 12.6 取出 H.264 裸流，再取一帧原始像素

从 MP4 中取出视频，不重新编码，并把长度前缀形式转换成适合 Annex B 裸流的表示：

```powershell
ffmpeg -n -i .\sample.mp4 -map 0:v:0 -c:v copy -bsf:v h264_mp4toannexb -f h264 .\sample.h264
```

`-map 0:v:0` 选择第一个输入的第一条视频流；`-bsf:v` 是视频码流过滤器，改变码流组织，不等于把视频重新压缩。裸流不保留原 MP4 完整的音频与时间信息，不能据此验证原来的音画同步。

再解码出第一张图像的 YUV420P 像素：

```powershell
ffmpeg -n -i .\sample.mp4 -map 0:v:0 -frames:v 1 -pix_fmt yuv420p -f rawvideo .\first.yuv
Get-Item .\first.yuv | Select-Object Name,Length
ffplay -f rawvideo -pixel_format yuv420p -video_size 640x360 -framerate 1 -i .\first.yuv
```

预期 `first.yuv` 大小为 `640×360×3/2 = 345,600 Byte`。该输出是工具写出的紧密原始帧，不含解码器内部可能存在的行对齐填充。

对照回答：`sample.mp4` 是容器，`sample.h264` 是压缩裸流，`first.yuv` 是未压缩像素，三者不能互换解释。也可以故意以错误宽高打开 `first.yuv`，观察为什么“读到数据”不代表“显示正确”。

### 13.3 综合作业 C：解释一个 RTSP 场景

**前置：**通过本章基础验收；这里不要求已经实现 RTSP。

假设客户端拿到以下信息：

```text
视频：H.264，1920×1080，30 fps，RTP clock rate 90000
音频：48 kHz、双声道，解码后 16 位 PCM
关键访问点：简化假设每 60 帧一个 IDR，参数集可用
当前视频显示队列：15 帧，平均帧间隔 1/30 秒
相邻视频图像 RTP 时间戳：345000 → 348000
```

不查代码，回答：

1. RTP 时间戳增量对应多少秒？能否由此判断每张图只有一个 RTP 包？
2. 一帧紧密 RGB24 与 YUV420P 分别多大？
3. 解码后的音频每秒多少字节？这能否当成网络音频码率？
4. 随机加入时，理想情况下等下个 IDR 可能要多久？
5. 15 帧队列对应多少媒体时间？若是紧密 YUV420P，像素数据约占多少 MB？
6. 只知道音频和视频各自的原始 RTP 时间戳，能否直接判断同步？还缺什么？
7. 画面持续发绿、花屏、越来越落后时，你会分别先检查哪类问题？

参考结论：增量 3000 对应 1/30 秒，但不能推断包数；RGB24 为 6,220,800 Byte、YUV420P 为 3,110,400 Byte；PCM 为 192,000 Byte/s，网络通常是压缩音频另加开销；理想等待范围约 0～2 秒；15 帧约 0.5 秒和 46.656 MB 像素数据；同步还需各自时钟频率与起点对应关系；偏色检查布局/范围/矩阵，花屏检查丢包/重组/参数/参考状态，积压检查处理速度与队列。

| §1.1：8 Mb/s，10 分钟 | `8,000,000 × 600 ÷ 8 = 600,000,000 Byte = 600 MB`，不含其他开销 |

| §4.2：25 fps | 固定帧间隔 40 ms，2 秒为 50 帧 |

| §5.3：纯色 | RGB24 纯红为每像素 `255,0,0`，纯绿为 `0,255,0`；交换 R/B 会红蓝互换 |
| §5.6：中性色度与大小 | U/V 都为 128 时颜色偏离接近零，改变 Y 可看灰阶；640×480 YUV420P 为 460,800 Byte |
| §6.4：改音调、时长、声道 | 只改 440→880 Hz，不改变数据量；3 秒单声道 PCM 288,000 Byte；3 秒双声道为 576,000 Byte，简单 WAV 再加 44 Byte 头 |
| §7.3：25 fps、每 50 帧 IDR | 简化周期为 2 秒；丢独立帧主要损失该画面，丢参考帧可能影响后面的依赖图像 |

### 15.1 本章来源与事实边界

本章根据本次“面向完全新手，先规划再逐点讲解，提供 Windows C++ 实验”的学习需求，扩展原有概念提纲。邻近笔记用于确定本章与 RTSP/RTP/解码章节的边界，不作为“项目功能已实现”的证据。上述流程、缓冲数字和同步阈值均为教学模型。

后续查证时优先阅读以下资料；标准较长，现在只需按问题查对应部分：

- [FFmpeg 命令行说明](https://ffmpeg.org/ffmpeg.html)：输入/输出选项、编码、流选择、码流复制。
- [ffprobe 说明](https://ffmpeg.org/ffprobe.html)：流、包、帧和 `read_intervals`。
- [FFmpeg 格式说明](https://ffmpeg.org/ffmpeg-formats.html)：容器与 rawvideo 等输入输出格式。
- [FFmpeg 码流过滤器说明](https://ffmpeg.org/ffmpeg-bitstream-filters.html#h264_005fmp4toannexb)：`h264_mp4toannexb`。
- [FFmpeg 缩放与色彩转换参数](https://ffmpeg.org/ffmpeg-scaler.html)：矩阵、范围、缩放。
- [ITU-T H.264 标准入口](https://www.itu.int/rec/T-REC-H.264)：NAL、参数集、编码图像和 Annex B 的规范出处。
- [RFC 3550](https://www.rfc-editor.org/rfc/rfc3550.html)：RTP/RTCP、时间戳、序号及 Sender Report。
- [RFC 6184](https://www.rfc-editor.org/rfc/rfc6184.html)：H.264 over RTP，尤其 90 kHz 时钟与 NAL 打包规则。
- [RFC 7587](https://www.rfc-editor.org/rfc/rfc7587.html)：Opus over RTP 的时钟与载荷规则。
- [Microsoft WAVEFORMATEX](https://learn.microsoft.com/en-us/windows/win32/api/mmreg/ns-mmreg-waveformatex)：PCM 的采样率、声道、位深、块对齐与字节率。
