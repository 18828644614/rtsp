# H.264 与 RTP 封装

> 适用对象：会 C++ 基础，但没有学过视频编码和媒体网络传输的读者。
>
> 学习目标：从 RTP 字节中取出完整的 H.264 NAL，处理单 NAL、STAP-A、FU-A，写成 Annex B 文件，再交给 FFmpeg 验证。Windows 和 Linux 的收包代码、编译和运行命令分别提供。
>
> 先看第 0 节，再按顺序学习。离线实验不需要摄像头、RTSP 服务器或 FFmpeg 开发库。文末区分作者实测和读者待运行项目；检查框由你完成后自行勾选。

## 0. 先规划：完整学习范围与顺序

### 0.1 这一章究竟在解决什么问题

摄像头产生的 H.264 数据通常不能原封不动地装进一个网络包：有的单元很小，可以几个一起运输；有的单元很大，需要拆成很多包。接收端必须按相同约定拆包、拼回去。

可以把流程想成运送一本书：H.264 规定“书的内容怎样写”，RTP 规定“运输标签怎样贴”，本章负责“拆箱、检查、按顺序还原书页”。还原后的书页仍是压缩数据，需要解码器才能变成画面。

```text
编码器 → H.264 NAL → RTP 打包 → UDP 或 RTSP/TCP → 网络
                                                    ↓
画面 ← 解码器 ← 完整 NAL / AU ← H.264 RTP 解包 ← RTP 解析与重排
```

本章完成的是中间的“从 RTP 到压缩码流”。它与 [[05-RTP协议]] 的通用包头、[[08-FFmpeg与解码]] 的像素输出衔接。

建议每次学习 45～90 分钟，代码实验可以拆成多次。下面的“产出”比学习天数更重要。

### 0.4 学完的最终标准

给你一份 SDP 和一组 RTP 包，你应该能说明：哪个 PT 是 H.264，包头有多长，载荷属于哪种打包方式，哪些字节是真正的 NAL，哪些包不能继续拼接，结果该如何交给解码器。还应能区分“字节拼对了”和“压缩内容确实能解码”两个验收层次。

## 1. 最小前置知识：只补本章用得到的部分

### 1.1 位、字节和十六进制

**前置：**C++ 整数和数组。

一个字节通常是 8 个二进制位，范围为 0～255。十六进制只是另一种写数字的方法：`0x65`、十进制 `101`、二进制 `01100101` 表示同一个数。下面的十六进制转储每两位代表一个字节，例如 `65 11 22` 是三个字节。

本章用 `std::uint8_t` 保存一个字节，用 `std::vector<std::uint8_t>` 保存字节数组。不要用带符号的 `char` 直接参与移位，也不要把网络字节强转成 C++ 位域结构体。

```cpp
std::uint8_t h = 0x65;
unsigned type = h & 0x1f;        // 保留低 5 位，得到 5
unsigned nri = (h >> 5) & 0x03; // 取中间 2 位，得到 3
unsigned forbidden = h >> 7;    // 取最高位，得到 0
```

`&` 是逐位“与”，可理解成用掩码遮住不需要的位；`>>` 把高处的位移到低处。`0x1f` 的二进制是 `00011111`，所以能保留低五位。

**常见错误：**把十六进制文本 `"65"` 的两个字符直接当作数值 `0x65`；把 `uint8_t` 打印成字符。观察数值时用 `static_cast<unsigned>(h)`。

**练习：**计算 `0x67 & 0x1f`、`0x68 & 0x1f`、`0x7c & 0x1f`。答案见 §17。

### 1.2 网络字节序：多字节整数怎样读

**前置：**§1.1。

RTP 和 STAP-A 的多字节字段使用**大端序**：高位字节在前。`00 04` 表示 4，不是 1024。

```cpp
// 调用前必须确认 p[0] 和 p[1] 确实存在。
std::uint16_t read_be16(const std::uint8_t* p) {
    return static_cast<std::uint16_t>(
        (static_cast<std::uint16_t>(p[0]) << 8) | p[1]);
}
```

不要用 `*reinterpret_cast<const uint16_t*>(p)` 直接读网络字段：除了大小端不同，还可能有对齐和对象访问规则问题。

**检查：**

- [ ] 我能把字节写成二进制，解释掩码和右移。
- [ ] 我知道读任何数组位置之前先验证长度。
- [ ] 我能解释为什么 `00 04` 应读成 4。

### 1.3 视频和网络的最小词典

| 词语 | 通俗解释 | 本章容易混淆的地方 |
| --- | --- | --- |
| 原始视频帧 | 可以用于显示的一张图像，例如 YUV 像素 | H.264 字节本身不是像素 |
| 编码/解码 | 按规则压缩图像 / 从压缩数据恢复图像 | 解包不等于解码 |
| 码流 | 编码后连续的压缩数据 | 不一定带 MP4 等容器 |
| RTP 包 | RTP 头和载荷组成的一次媒体传送单元 | 不等于一张图像 |
| 载荷 Payload | 协议头后面真正携带的内容 | RTP 载荷里还可能有 H.264 打包头 |
| UDP 数据报 | 保留消息边界的网络传送单元 | 仍可能丢失、重复和乱序 |
| TCP 字节流 | 有序可靠的连续字节 | 一次 `recv()` 不保留应用消息边界 |
| 裸流 | 不带 MP4 等容器的编码数据 | `.h264` 文件没有完整容器时间线 |

图像与帧率不熟时先读 [[02-音视频基础]]；Socket 不熟也可以先完成本章离线实验。

后面出现的 `fps` 表示每秒多少张图像，例如 30 fps 就是每秒 30 张。`API` 表示程序库提供给你的调用接口，例如“调用解码器函数”。“缓存/缓冲”是在暂时不能完成下一步时，先把数据存起来的一块内存。

## 2. 先分清四层：RTP 包、NAL、AU、画面

**前置：**§1.3。

### 2.1 NAL：编码流里的一块有类型的数据

**NAL Unit（网络抽象层单元，简称 NAL 或 NALU）**是 H.264 中的一种基本数据单元。普通 NAL 常见结构是：

```text
一个普通 H.264 NAL = 1 字节 NAL 头 + 后面的压缩数据或参数数据
```

NAL 可以装图像的一部分，也可以装参数或辅助信息。所以“数出了 100 个 NAL”不能推出“有 100 张图”。

### 2.2 Slice：一张编码图像的一部分

Slice 常译为“片”。一张编码图像可以由一个或多个 Slice 组成；这里先按常见逐行视频理解，不深入场图像与扩展编码。

例如一张图被编码成三个 Slice，每个 Slice 放在一个 NAL 中。只收到一个 Slice NAL，说明这一块完整，不代表整张图完整。

### 2.3 AU：一次解码访问单元

**Access Unit（访问单元，AU）**是一组有规定关联关系的 NAL；在本章常见逐行视频中，可把它理解为“一张编码图像所需的一组压缩数据”。AU 可以包含该图像的多个 Slice 和相关非图像 NAL。

```text
一个 AU： [相关辅助 NAL] [Slice NAL A] [Slice NAL B]
运输时：                 A → RTP 10、11、12
                        B → RTP 13
```

两个方向都可能发生：一个 RTP 包里有多个 NAL；一个 NAL 又可能分成多个 RTP 包。不要画成固定的一对一关系。

### 2.4 一张画面不是一个简单的网络计数

解码器可能需要参考先前图像，也可能因为重排而晚些输出图像。即使送入一个 AU，也不保证一次解码 API 调用立刻输出恰好一帧。

**练习：**一张图有 2 个 Slice，分别长 3000 和 500 字节。若每包目标最多携带约 1200 字节，能否断言“这张图就是两个 RTP 包”？

**检查：**

- [ ] 我能解释“一个 RTP 包 ≠ 一个 NAL ≠ 一个 AU”。
- [ ] 我知道 SPS/PPS 等 NAL 本身不是画面。

## 3. 看懂 NAL 头、SPS、PPS 和 IDR

### 3.1 NAL 头只有一字节，但必须先认对它

**前置：**§1.1、§2。

```text
bit：  7       6 5          4 3 2 1 0
      +---+-----------+----------------+
      | F |    NRI    |      Type      |
      +---+-----------+----------------+
```

- **F（forbidden_zero_bit）**：正常有效 NAL 应为 0。为 1 表示语法违规等异常；本章示例选择丢弃，不尝试容错解码。
- **NRI（nal_ref_idc）**：与参考重要性等有关的两位字段。先学会保存原值，不把它当作“清晰度等级”或唯一丢包优先级。
- **Type**：低 5 位，说明这个 NAL 是哪类内容。

| 常见 Type | 名称 | 初学时这样理解 |
| --- | --- | --- |
| 1 | 非 IDR 的编码 Slice | 可能是 I/P/B 等 Slice，不能只凭类型 1 判断为 P 帧 |
| 5 | IDR 图像的编码 Slice | 用于解码刷新；一个 IDR 图像可能有多个类型 5 NAL |
| 6 | SEI，补充增强信息 | 附加说明，某些内容还承载计时等信息 |
| 7 | SPS，序列参数集 | 解码一系列图像所需的公共配置 |
| 8 | PPS，图像参数集 | 更具体的编码配置，引用一个 SPS |
| 9 | AUD，访问单元分隔符 | 帮助分隔 AU；很多流不发送它 |
| 24 | STAP-A | RTP 聚合包的外层类型，不是原始图像 NAL 类型 |
| 28 | FU-A | RTP 分片包的外层类型，不是原始图像 NAL 类型 |

最后两行用于 RFC 6184 的 RTP 载荷结构。不能把它们的外层头直接写进 H.264 文件当普通 NAL。

例：`0x65 = 01100101`，所以 `F=0、NRI=3、Type=5`。`0x41` 的类型是 1，`0x67` 的类型是 7。

### 3.2 SPS 和 PPS：解码器先要拿到“说明书”

**前置：**§3.1。

SPS（Sequence Parameter Set，序列参数集）包含 profile、level、图像尺寸相关信息等；PPS（Picture Parameter Set，图像参数集）包含后续 Slice 需要的配置，并引用 SPS。Slice 自己通过参数集编号关联到 PPS。

这里 **profile（档次）**约定允许使用哪些编码工具，**level（级别）**约束解码处理能力相关上限，例如图像大小和处理速率。两者用于判断兼容性，不是简单的“画质好坏”评分。**参数集 ID**就是用来关联配置的一组编号。

```text
Slice → 引用某个 PPS → PPS 引用某个 SPS
```

把它想成“零件图纸”：收到零件还不够，还要拿到它使用的那一版图纸。不是随便找到一个 SPS 和一个 PPS 就一定匹配。

它们可能来自两个位置：

1. **带内**：在 RTP 媒体里，以单 NAL 或 STAP-A 等形式发送。
2. **带外**：在 SDP 的 `sprop-parameter-sets` 中给出，用 Base64 文本编码。

Base64 是“把二进制字节写成可打印文字”的方法，不是视频压缩算法。先解码 Base64 得到 NAL，再处理。不要把 Base64 字符串直接写进 `.h264`。

**常见错误：**每收一包就重复插入 SPS/PPS；只缓存最新一个参数集而不管编号；认为 SPS 固定位置就是宽高。完整解析 SPS 需要按比特读取语法、处理变长整数及裁剪等，不能靠固定偏移。

### 3.3 IDR、I、P、B：先分清“刷新”和“预测”

**前置：**§2、§3.2。

- I Slice 主要使用图像内信息编码。
- P/B Slice 可能引用其他图像，节省重复信息。
- **IDR（Instantaneous Decoding Refresh，即时解码刷新）**具有明确的参考刷新语义：在正确参数集和完整数据条件下，可以从这里重新开始解码后续图像，而不依赖 IDR 之前的参考图像。

不要把所有 I 图像都等同于 IDR。丢包后“等一张看起来是 I 的图”不是充分的恢复策略。本章入门方案使用“等待可用参数集和完整 IDR AU”作为恢复点；其他随机访问机制以后再学。

流中途加入后黑屏一会儿，可能正在等参数集或可用 IDR。若每 30 帧一个 IDR、帧率 30 fps，在无丢包且参数可用的理想条件下，等待可能接近 1 秒，而不是固定 1 秒。

### 3.4 字节拼接层不要擅自修改压缩内容

H.264 内部还会出现 RBSP、EBSP、仿竞争字节等术语。第一次只要知道：某些 `00 00 03` 中的 `03` 是为了防止内容与边界标记混淆而按规则插入的字节。**RTP 解包器应原样保留 NAL 内部编码字节**，不要顺手删除它们。

以后实现 SPS 语法解析时，再在专门的位流解析层按规则处理仿竞争字节。

**练习：**为什么有 SPS/PPS 但没有可用 IDR，仍可能无法从流中途正常播放？

**检查：**

- [ ] 我能从 `65`、`67`、`68` 手算类型。
- [ ] 我知道类型 1 不等于“肯定是 P 帧”。
- [ ] 我能解释参数集、IDR、普通 Slice 的不同职责。

## 4. 同一个 NAL，三种外部摆放方式

**前置：**§3。以下虚构 NAL `65 11 22 33` 只演示边界，不是可解码图像。

### 4.1 Annex B：前面放起始码

Annex B 是一种 H.264 字节流表示方式。常见边界形态为 `00 00 01` 或 `00 00 00 01`；四字节形态涉及额外零字节的规则，初学扫描时识别这两种即可。本章统一向每个 NAL 前写四字节形式：

```text
00 00 00 01 65 11 22 33
^^^^^^^^^^ ^^^^^^^^^^^
起始码      原始 NAL
```

起始码不属于 NAL 本体。`.h264` 裸流通常使用这种表示，适合本章保存和交给 FFmpeg 观察。

### 4.2 长度前缀：前面写 NAL 长度

MP4 中的 AVC 样本常使用长度前缀，相关配置保存在 `avcC`（AVCDecoderConfigurationRecord）中，开发中也常笼统称为 AVCC 格式。

假设配置规定使用 4 字节长度字段：

```text
00 00 00 04 65 11 22 33
^^^^^^^^^^ ^^^^^^^^^^^
长度为 4    4 字节 NAL
```

长度字段宽度由配置指定，不能无条件假设总是四字节。长度包含 NAL 头，不包含长度字段本身。起始码和长度字段不是同一种东西。

### 4.3 RTP 载荷：按 RFC 6184 运输 NAL

单 NAL 形式的 RTP 载荷直接是：

```text
65 11 22 33
```

没有 Annex B 起始码，也没有 MP4 长度前缀；STAP-A 和 FU-A 则有自己的运输头。必须先看打包方式，不能对所有 RTP 包都“去掉 12 字节，再补起始码”。

| 场景 | 边界从哪里知道 | 常见处理 |
| --- | --- | --- |
| Annex B 文件 | 起始码 | 扫描起始码得到 NAL |
| MP4 AVC 样本 | 配置指定宽度的长度字段 | 解容器后按长度切 NAL |
| 单 NAL RTP | RTP 载荷边界 | 整个载荷就是一个 NAL |
| STAP-A RTP | 包内每个 16 位长度字段 | 拆出多个 NAL |
| FU-A RTP | FU 起止标志及有序分片 | 重建一个完整 NAL |

**常见错误：**把起始码算入 STAP 的 NAL 长度；把 FU 头写进文件；每个 FU 都加起始码；删除 NAL 里面的 `03`。

**练习：**两个长度为 4 和 2 的 NAL，用四字节起始码写成 Annex B 共多少字节？若用四字节长度前缀又是多少？大小相同能证明格式相同吗？

**检查：**

- [ ] 我能辨认起始码、长度字段、NAL 本体。
- [ ] 我知道 RTP 解包完成后，才选择输出 Annex B 或其他接口格式。

## 5. 在碰载荷前，先检查 SDP 和 RTP 边界

### 5.1 SDP 决定 PT 的含义和允许的打包方式

**前置：**§1～§4；SDP 详细解释见 [[04-SDP会话描述]]。

```sdp
m=video 0 RTP/AVP 96
a=rtpmap:96 H264/90000
a=fmtp:96 packetization-mode=1
```

这里 `96` 是该媒体轨道中的 Payload Type（载荷类型编号，PT），在这份描述中对应 H.264。换一条轨道或一份 SDP，96 可能代表别的格式，不能写死“96 永远是 H.264”。`90000` 是 RTP 计时时钟每秒刻度数，不是每秒 90000 帧。

`m=` 的端口 `0` 在 RTSP 单播描述中有特定语境；接收端口由你配置或通过 SETUP 协商，不直接拿这里的 0 收包。

| packetization-mode | 名称 | 本章涉及的允许形式 |
| --- | --- | --- |
| 0 | Single NAL Unit Mode，单 NAL 模式 | 单 NAL；不允许 STAP-A/FU-A |
| 1 | Non-Interleaved Mode，非交织模式 | 单 NAL、STAP-A、FU-A |
| 2 | Interleaved Mode，交织模式 | 涉及 STAP-B、MTAP、FU-B、DON 等；本章不实现 |

**缺少 `packetization-mode` 时，RFC 6184 默认值是 0。**不能因为设备“经常使用模式 1”就把缺省值当成 1。

这里的“交织模式”是 H.264 NAL 发送顺序的术语；RTSP 的 TCP interleaved 是把 RTP/RTCP 放在 TCP 连接中的运输方式。两者不是同一开关。TCP 交织传输时，H.264 仍可为 `packetization-mode=1`。

### 5.2 RTP 头不总是 12 字节

**前置：**§1.2。

```text
第 0 字节：V(2 位) P(1 位) X(1 位) CC(4 位)
第 1 字节：M(1 位) PT(7 位)
第 2～3 字节：Sequence Number，16 位包序号
第 4～7 字节：Timestamp，32 位媒体时间戳
第 8～11 字节：SSRC，32 位同步源标识
后面可能有：CC 个 4 字节 CSRC、扩展头、载荷、末尾填充
```

V 是版本，应为 2；CC 是附加源标识数量；X 表示扩展头；P 表示包尾有填充。扩展头先有 4 字节信息，其中长度以 **32 位字，即每单位 4 字节**计数。P 为 1 时，最后一个字节给出填充总长度，包含这个长度字节自身。

安全解析顺序：

1. 检查至少 12 字节，版本为 2。
2. 计算 `12 + 4 * CC`，验证没有越界。
3. X 为 1 时，读扩展头及长度，验证后跳过。
4. P 为 1 时，从包尾扣除合法填充，禁止扣到头部里。
5. 取出真正载荷；它不能为空。
6. 按 PT 和媒体轨道选解包器，按 SSRC 维护各自状态。

若收到 RTSP TCP 数据，应先解析 `$ + channel + 16位长度 + 内容` 的交织外层，再拿出完整 RTP 包。不要把 `$` 交给本章 RTP 解析函数。RTCP 也应按协商通道或端口分流，不当成 H.264。

**常见错误：**固定从 `packet + 12` 开始；把扩展长度当字节数；没去掉 Padding；把 PT 与 NAL Type 当成同一字段。

## 6. 两种先学会的打包方式：单 NAL 与 STAP-A

### 6.1 Single NAL Unit：一个 RTP 载荷装一个 NAL

**前置：**§3～§5。

载荷第一个字节的低 5 位为 1～23 时，属于 RFC 6184 的单 NAL 运输范围。常见有效类型见 §3；范围中有保留或扩展值，具体语义应按 H.264 对应规范处理。

```text
RTP 头 | 67 42 ...
         └─ 完整 SPS NAL
输出：00 00 00 01 67 42 ...
```

不必去掉 NAL 头；`67` 本来就属于 NAL。长度为 0 必须拒绝。外层保留类型 0、30、31 应忽略，不能当作正常图像写出。

### 6.2 STAP-A：一个 RTP 载荷装多个小 NAL

**前置：**§1.2、§6.1。

STAP-A（Single-Time Aggregation Packet A，单时间聚合包 A）把同一采样时间关联的小 NAL 放在一个包里。它常用来一起运输 SPS 和 PPS，但不限于这两种 NAL。

```text
结构：STAP-A头 | 长度1(2字节) | NAL1 | 长度2(2字节) | NAL2 ...
例子：78 00 04 67 42 00 1e 00 02 68 ce
```

`0x78 & 0x1f = 24`，说明外层是 STAP-A。拆开得到：

```text
NAL 1：67 42 00 1e，长度 4，包含 67 这个 NAL 头
NAL 2：68 ce，长度 2，包含 68 这个 NAL 头
```

这只是教学字节，不保证这些参数集内容能被解码器接受。

处理步骤是“跳过 1 字节外层头 → 读两字节大端长度 → 验证 → 取 NAL → 重复”。长度不包括自己；内部 NAL 前没有 Annex B 起始码。包总长为 `1 + (2 + 4) + (2 + 2) = 11` 字节。

**同时防住：**不足两字节的长度字段、零长度、长度超过剩余字节、内部嵌套 STAP/FU。教学程序先验证整个 STAP-A，再一次性返回各个 NAL，避免“前半个聚合包已经写出，后半段才发现损坏”。

## 7. FU-A：把一个大 NAL 分片再拼回来

### 7.1 为什么要分片

**前置：**§6。

路径 MTU 是网络路径上希望一次运输的数据大小上限。以常见 MTU 1500、IPv4 无选项为例，扣掉 20 字节 IP 头、8 字节 UDP 头、12 字节最小 RTP 头，只剩 1460 字节放 RTP 载荷。实际还有 IPv6、扩展、隧道等，不能把 1460 当作固定安全值。

FU-A 载荷还要用 2 字节分片头。如果选择“RTP 载荷最多 1200 字节”的教学策略，每个 FU 的 NAL 内容片段最多 1198 字节。1200 是人为目标，不是协议常量。

不要依赖 IP 分片解决所有大 NAL；IP 分片中丢一片，整份上层数据报通常就不能交付。

### 7.2 一个 FU-A 载荷的结构

```text
FU indicator（1字节） | FU header（1字节） | 一段原始 NAL 内容

FU indicator： F(1) NRI(2) Type=28(5)
FU header：    S(1) E(1) R(1) 原始 Type(5)
```

- S（Start）为 1：这是这个 NAL 的第一个片段。
- E（End）为 1：这是最后一个片段。
- R 为保留位：发送方必须为 0，接收方按 RFC 忽略它。
- S 和 E 不能同时为 1；一个 FU-A 就结束的做法不符合规则。
- 原始 NAL 的一字节头没有原样放在片段内容里，要从两个 FU 字节恢复。
- RFC 允许 FU 内容为空，所以最短合法 FU-A 载荷可仅有两个头字节，不能无条件要求至少 3 字节。

重建头：

```cpp
std::uint8_t original_header =
    (fu_indicator & 0xe0) | (fu_header & 0x1f);
```

`0xe0` 保留 F 与 NRI，`0x1f` 取原始 Type。不要把 28 当成重建后的类型。

### 7.3 按字节走一遍完整重组

假设原 NAL 是 `65 11 22 33 44 55 66`，运输时拆成：

| RTP 序号 | RTP 时间戳 | FU-A 载荷 | 含义 |
| --- | --- | --- | --- |
| 101 | 90000 | `7c 85 11 22` | S=1、E=0，原类型 5，开始 |
| 102 | 90000 | `7c 05 33 44` | S=0、E=0，中间 |
| 103 | 90000 | `7c 45 55 66` | S=0、E=1，结束 |

第一包：`(0x7c & 0xe0) | (0x85 & 0x1f) = 0x65`，先放重建头 `65`，再放 `11 22`。后续只拼内容，不再次补 NAL 头。最后写成 Annex B：

```text
00 00 00 01 65 11 22 33 44 55 66
```

一个完整 NAL 只有一个起始码；各 FU 之间没有起始码。

### 7.4 重组至少要记住什么

**前置：**§7.3。

每个源至少维护：是否正在重组、SSRC、时间戳、下一预期序号、重建的 NAL 头、已收字节、开始/最近更新时间。SSRC 是“这一路是谁”，时间戳是“哪个媒体时刻”，序号用于发现缺口。

| 收到什么 | 基本动作 |
| --- | --- |
| 合法 Start | 开新 NAL；若旧 NAL 未结束，先丢弃旧缓冲并记录 |
| 无 Start 却收到中间/结束片段 | 丢弃，不能凭空恢复开头 |
| 连续、同源、同时间戳、同原始头的中间片段 | 追加内容 |
| 合法 End | 追加后提交完整 NAL，清空状态 |
| 序号缺失且已超过重排等待范围 | 丢弃未完成 NAL；拒绝其后续片段 |
| 重组中时间戳或原始头变化 | 中止旧 NAL，不拼到一起 |
| 超时或超过配置大小 | 中止并释放缓冲，等待新 Start |

序号是 16 位，会从 65535 回到 0。连续性检查使用无符号回绕，例如：

```cpp
std::uint16_t expected = static_cast<std::uint16_t>(previous + 1u);
```

真实 UDP 接收端要先重排，不能收到 `101、103、102` 就立即当成永远丢了 102。第 9 节为突出解包，只接受已排好序的输入；它会保守丢弃乱序分片，绝不悄悄拼错。

**常见错误：**丢了 102 仍把 101、103 拼成“完整 NAL”；重复追加重传包；混入别的 SSRC；等不到 End 就无限占内存。

**练习：**只收到 101、103，能否写出 `65 11 22 55 66` 当作完整 NAL？

- [ ] 我会在 End 到达且完整时提交 NAL。

## 8. 时间戳、Marker 和完整图像：区分两种“结束”

### 8.1 序号和时间戳分工不同

**前置：**§5、§7。

序号通常每发一个 RTP 包加 1。H.264 RTP 时间戳使用 90 kHz 时钟，表示媒体采样时刻；同一图像关联的多个包通常使用相同时间戳。

固定 30 fps、无复杂重排时，相邻图像常相差 `90000 / 30 = 3000` 个刻度。一个 AU 分成 10 个包，不是每个包都加 3000。25 fps 的常见增量为 3600，10 fps 为 9000。

有 B 图像时，发送/解码顺序与显示顺序可能不同，时间戳在到达顺序上不一定单调增加。不能用“时间戳变小”直接判损坏，也不能拿不同 SSRC 的原始时间戳直接相减做同步，详见 [[06-RTCP协议]]。

### 8.2 FU 的 E 位结束 NAL，RTP 的 M 位提示 AU 末包

Marker（M）在 RFC 6184 中标记由 RTP 时间戳指示的访问单元的最后一个包。它能帮助判断 AU 结束，但接收端不能只依赖它。

```text
同一个 AU，两个 Slice NAL：
RTP 10：Slice A 的 FU Start     E=0  M=0
RTP 11：Slice A 的 FU End       E=1  M=0  ← 只结束了 A
RTP 12：完整 Slice B 单 NAL           M=1  ← AU 的末包
```

M 不表示关键帧、不表示第一个包，也不证明前面的包都到齐。若 RTP 11 丢了，即使 RTP 12 的 M=1，这张图仍然缺数据。

STAP-A 携带多个 NAL 时只有一个 RTP M 位，不能给内部每个 NAL 都生搬相同的“图像结束”结论。

### 8.3 完整 NAL 和完整 AU 是两项验收

本章 C++ 示例按 NAL 写文件，没有实现事务式 AU 组装。如果 AU 有两个 Slice，其中一个丢了，另一个完整 Slice 仍可能已经写出。因此它适合学习和无丢包实验，不能保证每张恢复出的图像完整。

完整客户端应在重排后维护 AU 状态：结合时间戳、序号、M、可用 AUD 和必要的 Slice 语法/成熟解析器判断边界；发现缺失时标记 AU 损坏，按策略丢弃，并评估参考图像是否受影响。只比较相邻时间戳不能涵盖所有码流。

### 8.4 时间戳也会回绕，但不要拿它代替包序号

32 位时间戳按 90 kHz 运行，大约每 `2^32 / 90000 ≈ 47722` 秒，也就是 13.26 小时走一圈。例如 `fffffff0` 后前进 48 个刻度会变成 `00000020`。短间隔、已经明确是正向媒体时间差的场景，可用无符号差值处理回绕：

```cpp
std::uint32_t previous_ts = 0xfffffff0u;
std::uint32_t current_ts = 0x00000020u;
std::uint32_t ticks = current_ts - previous_ts; // 48
double seconds = ticks / 90000.0;
```

该片段不是通用时间排序器：存在 B 图像、长时间断流或多次回绕时，还要结合上下文扩展时间线；不能把任意两个到达包的无符号差值都当正向播放间隔。FU 重组只要求同一 NAL 的时间戳一致，连续性由包序号检查。

## 9. C++ 实验一：可在两个系统运行的离线解包器

### 9.1 文件和接口先说明白

**前置：**§1～§8，C++17 编译器。第一遍先读调用流程，不必一次记住全部代码。

本节保存为 `h264_lab.cpp`，Windows/Linux 使用**同一份标准 C++ 代码**。操作系统专属 Socket 代码分别放在 §12，避免把字节重组和网络 API 混在一起。

```text
packets.txt：每行一份完整 RTP 包，以两位十六进制表示每个字节
    ↓ read_hex：文本转成字节
    ↓ parse_rtp：验证 RTP，去掉头、扩展、Padding
    ↓ Depacketizer::push：按单 NAL / STAP-A / FU-A 还原
    ↓ 完整 NAL 前添加 00 00 00 01
output.h264：Annex B 二进制文件
```

程序支持模式 0、1，必须从命令行明确提供 PT 和模式。它锁定首个选中 PT 包的 SSRC；混入其他 SSRC 会报错，切流需要重新启动实例。它会检测序号缺口但**不重排、不去重、不重传**，因此乱序输入可能被保守丢弃。正常模式使用退出码 0；输入/文件错误用 1；发生丢包或内容丢弃用 2，输出中仍可能保留其他有效 NAL。

单 NAL 上限示例设置为 8 MiB，用于防止无限缓冲，不是 H.264 协议上限。离线实验在文件结束时丢弃未完成 FU；在线版本还需要时间超时、包数上限等机制。

### 9.2 完整代码：h264_lab.cpp

```cpp
#include <cstdint>
#include <fstream>
#include <iostream>
#include <sstream>
#include <stdexcept>
#include <string>
#include <utility>
#include <vector>

using Bytes = std::vector<std::uint8_t>;
constexpr std::size_t MAX_NAL = 8u * 1024u * 1024u;

std::uint16_t be16(const Bytes& b, std::size_t i) {
    return static_cast<std::uint16_t>(
        (static_cast<std::uint16_t>(b[i]) << 8) | b[i + 1]);
}

std::uint32_t be32(const Bytes& b, std::size_t i) {
    return (std::uint32_t{b[i]} << 24) |
           (std::uint32_t{b[i + 1]} << 16) |
           (std::uint32_t{b[i + 2]} << 8) | b[i + 3];
}

Bytes read_hex(std::string line) {
    // 支持 # 注释；每个字节必须写成两位十六进制。
    line = line.substr(0, line.find('#'));
    std::istringstream in(line);
    std::string word;
    Bytes b;
    while (in >> word) {
        if (word.size() != 2 ||
            word.find_first_not_of("0123456789abcdefABCDEF") !=
                std::string::npos)
            throw std::runtime_error("invalid hex byte");
        b.push_back(static_cast<std::uint8_t>(std::stoul(word, nullptr, 16)));
        if (b.size() > 65535)
            throw std::runtime_error("RTP packet exceeds lab limit");
    }
    return b;
}

struct Rtp {
    unsigned pt{};
    bool marker{};
    std::uint16_t seq{};
    std::uint32_t ts{}, ssrc{};
    Bytes payload;
};

Rtp parse_rtp(const Bytes& b) {
    if (b.size() < 12 || (b[0] >> 6) != 2)
        throw std::runtime_error("short RTP header or wrong version");
    std::size_t pos = 12 + 4u * (b[0] & 0x0f);
    if (pos > b.size())
        throw std::runtime_error("truncated CSRC list");
    if (b[0] & 0x10) {
        if (b.size() - pos < 4)
            throw std::runtime_error("short RTP extension header");
        const std::size_t ext = 4u * be16(b, pos + 2);
        pos += 4;
        if (ext > b.size() - pos)
            throw std::runtime_error("truncated RTP extension data");
        pos += ext;
    }
    std::size_t end = b.size();
    if (b[0] & 0x20) {
        const std::size_t padding = b.back();
        if (padding == 0 || padding > end - pos)
            throw std::runtime_error("invalid RTP padding");
        end -= padding;
    }
    if (pos >= end)
        throw std::runtime_error("empty RTP payload");
    Rtp r;
    r.pt = b[1] & 0x7f;
    r.marker = (b[1] & 0x80) != 0;
    r.seq = be16(b, 2);
    r.ts = be32(b, 4);
    r.ssrc = be32(b, 8);
    r.payload.assign(b.begin() + pos, b.begin() + end);
    return r;
}

void check_nal(const Bytes& n) {
    if (n.empty() || n.size() > MAX_NAL || (n[0] & 0x80))
        throw std::runtime_error("empty, oversized or F=1 NAL");
    const unsigned t = n[0] & 0x1f;
    if (t < 1 || t > 23)
        throw std::runtime_error("invalid original NAL type");
}

class Depacketizer {
    unsigned pt_, mode_;
    bool source_known_ = false, seq_known_ = false, active_ = false;
    std::uint32_t source_ = 0, fu_ts_ = 0;
    std::uint16_t previous_ = 0;
    std::uint8_t fu_header_ = 0;
    Bytes fu_;

    void interrupt(const char* why) {
        if (active_) {
            std::cerr << "discard unfinished FU: " << why << '\n';
            ++warnings;
        }
        reset_fu();
    }

public:
    unsigned warnings = 0;
    Depacketizer(unsigned pt, unsigned mode) : pt_(pt), mode_(mode) {}

    void reset_fu() {
        active_ = false;
        fu_.clear();
    }

    void finish() { interrupt("end of input"); }

    std::vector<Bytes> push(const Rtp& r) {
        if (r.pt != pt_) return {}; // 其他编码交给别的处理器。
        if (!source_known_) {
            source_ = r.ssrc;
            source_known_ = true;
        }
        if (r.ssrc != source_)
            throw std::runtime_error("SSRC changed: use a new instance");
        if (seq_known_ &&
            r.seq != static_cast<std::uint16_t>(previous_ + 1u)) {
            std::cerr << "sequence discontinuity at " << r.seq << '\n';
            ++warnings;
            reset_fu();
        }
        seq_known_ = true;
        previous_ = r.seq;

        const Bytes& p = r.payload;
        if (p.empty() || (p[0] & 0x80))
            throw std::runtime_error("empty payload or F=1");
        const unsigned type = p[0] & 0x1f;
        // RFC 6184 的外层保留类型忽略，不输出为 NAL。
        if (type == 0 || type >= 30) {
            interrupt("reserved packet type");
            return {};
        }
        if (type >= 1 && type <= 23) {
            interrupt("single NAL arrived");
            check_nal(p);
            return {p};
        }
        if (mode_ != 1)
            throw std::runtime_error("aggregation/FU is not allowed in mode 0");

        if (type == 24) { // STAP-A：先验证全部，再提交。
            interrupt("STAP-A arrived");
            std::vector<Bytes> result;
            std::size_t pos = 1;
            while (pos < p.size()) {
                if (p.size() - pos < 2)
                    throw std::runtime_error("short STAP length");
                const std::size_t size = be16(p, pos);
                pos += 2;
                if (size == 0 || size > p.size() - pos)
                    throw std::runtime_error("invalid STAP NAL length");
                Bytes n(p.begin() + pos, p.begin() + pos + size);
                check_nal(n);
                result.push_back(std::move(n));
                pos += size;
            }
            if (result.empty())
                throw std::runtime_error("empty STAP-A");
            return result;
        }

        if (type != 28)
            throw std::runtime_error("unsupported packet type (mode 2?)");
        if (p.size() < 2)
            throw std::runtime_error("short FU header");
        const bool start = (p[1] & 0x80) != 0;
        const bool end = (p[1] & 0x40) != 0;
        // 保留位 R 不参与判断：接收方按 RFC 忽略。
        const auto original = static_cast<std::uint8_t>(
            (p[0] & 0xe0) | (p[1] & 0x1f));
        if ((start && end) || (original & 0x1f) == 0 ||
            (original & 0x1f) > 23)
            throw std::runtime_error("invalid FU flags or original type");
        if (start) {
            interrupt("new FU start");
            active_ = true;
            fu_ts_ = r.ts;
            fu_header_ = original;
            fu_.push_back(original);
        } else if (!active_) {
            throw std::runtime_error("FU continuation without start");
        }
        if (r.ts != fu_ts_ || original != fu_header_)
            throw std::runtime_error("FU timestamp or NAL header changed");
        if (p.size() - 2 > MAX_NAL - fu_.size())
            throw std::runtime_error("FU exceeds NAL size limit");
        fu_.insert(fu_.end(), p.begin() + 2, p.end());
        if (!end) return {};
        check_nal(fu_);
        Bytes complete = std::move(fu_);
        reset_fu();
        return {std::move(complete)};
    }
};

int number(const char* text, int maximum) {
    std::size_t used = 0;
    int n = std::stoi(text, &used);
    if (text[used] != '\0' || n < 0 || n > maximum)
        throw std::runtime_error("invalid PT or mode");
    return n;
}

int main(int argc, char** argv) {
    if (argc != 5) {
        std::cerr << "usage: h264_lab packets.txt output.h264 PT mode\n";
        return 1;
    }
    try {
        const auto pt = static_cast<unsigned>(number(argv[3], 127));
        const auto mode = static_cast<unsigned>(number(argv[4], 1));
        // 输入和输出必须是两个不同文件；输出会截断已有文件。
        if (std::string(argv[1]) == argv[2])
            throw std::runtime_error("input and output must differ");
        std::ifstream in(argv[1]);
        if (!in) throw std::runtime_error("cannot open input");
        std::ofstream out(argv[2], std::ios::binary);
        if (!out) throw std::runtime_error("cannot open output");
        Depacketizer dep(pt, mode);
        std::string line;
        std::size_t line_no = 0, packets = 0, nals = 0, dropped = 0;
        const char prefix[4] = {0, 0, 0, 1};
        while (std::getline(in, line)) {
            ++line_no;
            std::vector<Bytes> ready;
            try {
                if (line.size() > 200000)
                    throw std::runtime_error("hex line too long");
                Bytes b = read_hex(line);
                if (b.empty()) continue;
                Rtp r = parse_rtp(b);
                ++packets;
                ready = dep.push(r);
            } catch (const std::exception& e) {
                std::cerr << "drop line " << line_no << ": " << e.what() << '\n';
                ++dropped;
                dep.reset_fu();
                continue;
            }
            for (const auto& n : ready) {
                out.write(prefix, 4);
                out.write(reinterpret_cast<const char*>(n.data()),
                          static_cast<std::streamsize>(n.size()));
                if (!out) throw std::runtime_error("output write failed");
                ++nals;
                std::cout << "NAL type=" << unsigned(n[0] & 0x1f)
                          << " bytes=" << n.size() << '\n';
            }
        }
        if (in.bad()) throw std::runtime_error("input read failed");
        dep.finish();
        out.close();
        if (!out) throw std::runtime_error("output close failed");
        std::cout << "packets=" << packets << " nals=" << nals
                  << " dropped=" << dropped
                  << " warnings=" << dep.warnings << '\n';
        if (packets == 0 || nals == 0) return 2;
        return (dropped || dep.warnings) ? 2 : 0;
    } catch (const std::exception& e) {
        std::cerr << "fatal: " << e.what() << '\n';
        return 1;
    }
}
```

### 9.3 不要跳过的代码阅读顺序

1. 先看 `main`：每行输入变成一包，一包可能输出零个、一个或多个 NAL。
2. 看 `parse_rtp`：所有长度验证发生在对应字节访问之前。
3. 看 `type` 的分支：单包直接返回；STAP 拆出一组；FU 需要保存跨包状态。
4. 看 FU Start：只在这里创建原始 NAL 头；后续片段只复制 `p[2...]`。
5. 看 End 与异常路径：成功才返回，失败清空未完成缓冲。
6. 看 `out.write`：二进制写入，不能用字符串结束符判断内容长度。

为降低第一次运行门槛，程序不会自动解析 SDP、解码 Base64、缓存参数集或等待 IDR。真实流依赖发送端重复发送带内 SPS/PPS，后面的命令会明确设置。学习这些工程接口时读 §15。

## 12. C++ 实验二：Windows/Linux 分开的 UDP 收包代码

### 12.1 这两个程序负责什么

**前置：**完成离线实验；了解 IP 与端口即可。接收器只绑定本机回环地址 `127.0.0.1:5004`，用于本机实验，不接摄像头或局域网其他机器。

它们把每个 UDP 数据报原样写成 `live_packets.txt` 的一行，供离线解包器复用。这样你可以反复分析同一份网络数据，而不用每次都重新发流。它们不是抓包工具的替代品，也不解析 RTSP。

接收器启动后最多等首包 30 秒；收过包后，连续 3 秒无数据就结束；最多保存 20000 包。本实验只有 2 秒视频，正常不会碰到上限。超时是实验停止条件，不是用于判定每个媒体帧边界的依据。

### 12.2 Windows 专用：udp_capture_win.cpp

Windows 使用 Winsock，需要 `WSAStartup`、`closesocket` 和链接 `ws2_32`。与 Linux 的函数同名不代表类型和错误码相同。

```cpp
#ifndef WIN32_LEAN_AND_MEAN
#define WIN32_LEAN_AND_MEAN
#endif
#include <winsock2.h>
#include <ws2tcpip.h>
#include <fstream>
#include <iomanip>
#include <iostream>
#include <stdexcept>
#include <string>

int main() {
    WSADATA wsa{};
    const int init = WSAStartup(MAKEWORD(2, 2), &wsa);
    if (init != 0) {
        std::cerr << "WSAStartup failed: " << init << '\n';
        return 1;
    }
    SOCKET sock = INVALID_SOCKET;
    int result = 0;
    try {
        auto fail = [](const char* what) {
            throw std::runtime_error(std::string(what) + ": " +
                                     std::to_string(WSAGetLastError()));
        };
        sock = socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP);
        if (sock == INVALID_SOCKET) fail("socket");
        int buffer_size = 1024 * 1024;
        if (setsockopt(sock, SOL_SOCKET, SO_RCVBUF,
                       reinterpret_cast<const char*>(&buffer_size),
                       sizeof(buffer_size)) == SOCKET_ERROR) fail("SO_RCVBUF");
        auto timeout = [&](DWORD ms) {
            if (setsockopt(sock, SOL_SOCKET, SO_RCVTIMEO,
                           reinterpret_cast<const char*>(&ms),
                           sizeof(ms)) == SOCKET_ERROR) fail("SO_RCVTIMEO");
        };
        timeout(30000);
        sockaddr_in local{};
        local.sin_family = AF_INET;
        local.sin_port = htons(5004);
        local.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
        if (bind(sock, reinterpret_cast<const sockaddr*>(&local),
                 sizeof(local)) == SOCKET_ERROR) fail("bind");
        std::ofstream out("live_packets.txt");
        if (!out) throw std::runtime_error("cannot open live_packets.txt");
        out << std::hex << std::setfill('0');
        std::cout << "Listening on 127.0.0.1:5004; start FFmpeg now.\n";
        unsigned count = 0;
        char buffer[65536];
        while (count < 20000) {
            int n = recvfrom(sock, buffer, sizeof(buffer), 0, nullptr, nullptr);
            if (n == SOCKET_ERROR) {
                if (WSAGetLastError() == WSAETIMEDOUT && count != 0) break;
                fail("recvfrom (first packet must arrive within 30 seconds)");
            }
            if (n == 0) continue;
            if (count == 0) timeout(3000);
            for (int i = 0; i < n; ++i)
                out << std::setw(2)
                    << static_cast<unsigned>(static_cast<unsigned char>(buffer[i]))
                    << (i + 1 == n ? '\n' : ' ');
            if (!out) throw std::runtime_error("capture write failed");
            ++count;
        }
        out.close();
        if (!out) throw std::runtime_error("capture close failed");
        std::cout << "saved packets=" << count << '\n';
    } catch (const std::exception& e) {
        std::cerr << e.what() << '\n';
        result = 1;
    }
    if (sock != INVALID_SOCKET) closesocket(sock);
    WSACleanup();
    return result;
}
```

### 12.3 Linux 专用：udp_capture_linux.cpp

Linux 使用 POSIX Socket，错误码在 `errno`，超时使用 `timeval`，释放句柄使用 `close`。本程序显式处理被信号中断的 `EINTR`。

```cpp
#include <arpa/inet.h>
#include <sys/socket.h>
#include <sys/time.h>
#include <unistd.h>
#include <cerrno>
#include <cstring>
#include <fstream>
#include <iomanip>
#include <iostream>
#include <stdexcept>
#include <string>

int main() {
    int sock = -1;
    int result = 0;
    try {
        auto fail = [](const char* what) {
            throw std::runtime_error(std::string(what) + ": " + std::strerror(errno));
        };
        sock = socket(AF_INET, SOCK_DGRAM, 0);
        if (sock < 0) fail("socket");
        int buffer_size = 1024 * 1024;
        if (setsockopt(sock, SOL_SOCKET, SO_RCVBUF, &buffer_size,
                       sizeof(buffer_size)) < 0) fail("SO_RCVBUF");
        auto timeout = [&](int seconds) {
            timeval value{};
            value.tv_sec = seconds;
            if (setsockopt(sock, SOL_SOCKET, SO_RCVTIMEO,
                           &value, sizeof(value)) < 0) fail("SO_RCVTIMEO");
        };
        timeout(30);
        sockaddr_in local{};
        local.sin_family = AF_INET;
        local.sin_port = htons(5004);
        local.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
        if (bind(sock, reinterpret_cast<const sockaddr*>(&local),
                 sizeof(local)) < 0) fail("bind");
        std::ofstream out("live_packets.txt");
        if (!out) throw std::runtime_error("cannot open live_packets.txt");
        out << std::hex << std::setfill('0');
        std::cout << "Listening on 127.0.0.1:5004; start FFmpeg now.\n";
        unsigned count = 0;
        unsigned char buffer[65536];
        while (count < 20000) {
            const ssize_t n = recvfrom(sock, buffer, sizeof(buffer), 0, nullptr, nullptr);
            if (n < 0) {
                if (errno == EINTR) continue;
                if ((errno == EAGAIN || errno == EWOULDBLOCK) && count != 0) break;
                fail("recvfrom (first packet must arrive within 30 seconds)");
            }
            if (n == 0) continue;
            if (count == 0) timeout(3);
            for (ssize_t i = 0; i < n; ++i)
                out << std::setw(2) << static_cast<unsigned>(buffer[i])
                    << (i + 1 == n ? '\n' : ' ');
            if (!out) throw std::runtime_error("capture write failed");
            ++count;
        }
        out.close();
        if (!out) throw std::runtime_error("capture close failed");
        std::cout << "saved packets=" << count << '\n';
    } catch (const std::exception& e) {
        std::cerr << e.what() << '\n';
        result = 1;
    }
    if (sock >= 0) close(sock);
    return result;
}
```

```bash

```

### 12.4 读懂两个系统的差异

| 项目 | Windows | Linux |
| --- | --- | --- |
| 初始化 | `WSAStartup` | 无此步骤 |
| Socket 类型 | `SOCKET` | `int` |
| 失败返回 | `INVALID_SOCKET` / `SOCKET_ERROR` | 通常为 -1 |
| 获取错误 | `WSAGetLastError()` | `errno` / `strerror` |
| 收包超时参数 | `DWORD`，毫秒 | `timeval`，秒和微秒 |
| 关闭 | `closesocket`，最后 `WSACleanup` | `close` |
| 额外链接 | MSVC `ws2_32.lib`，MinGW `-lws2_32` | 本例无需额外库 |

**常见错误：**先启动发送器导致头几包丢失；两个进程占用同一个 5004 端口；Windows 用 `close` 关 Socket；Linux 给 `SO_RCVTIMEO` 传一个毫秒整数；把 `live_packets.txt` 当二进制 H.264 播放。

## 13. 真实视频实验：从 FFmpeg 发 RTP，再恢复图像

### 13.1 实验依赖和参数含义

**前置：**完成 §11～§12，安装 FFmpeg CLI（命令行工具），不需要 FFmpeg C++ 头文件或库。

Windows 从 [FFmpeg 下载入口](https://ffmpeg.org/download.html)选择预编译包，把 `bin` 加到 PATH，再开新终端。Linux 可使用 §11 的包管理器安装。先确认：

```text
ffmpeg -version
ffprobe -version
```

本实验用 `testsrc2` 生成测试图，不需要摄像头。关键选项如下：

| 选项 | 为什么用 |
| --- | --- |
| `-re` | 以接近实时速度发送，便于观察；这是输入选项 |
| `-f lavfi -i testsrc2=size=320x240:rate=10` | 生成 320×240、10 fps 测试视频 |
| `-t 2` | 只发 2 秒，目标为 20 张图像 |
| `-an` | 不发音频，先只处理一条轨道 |
| `-c:v libx264` | 选择 H.264 编码器，当前 FFmpeg 构建必须带它 |
| `-preset ultrafast -tune zerolatency` | 降低本实验编码等待，具体码率并非最优 |
| `-pix_fmt yuv420p -bf 0` | 使用常见像素格式，不用 B 图像降低理解难度 |
| `-g 10` | 设置关键图像间隔的编码约束，结合下一行固定实验行为 |
| `repeat-headers=1:aud=1:keyint=10:min-keyint=10:scenecut=0` | 重复带内参数集，带 AUD，并控制 IDR 间隔 |
| `-payload_type 96` | 显式指定本次 RTP PT |
| `-sdp_file live.sdp` | 保存此次编码的 SDP，供你核对 |
| `pkt_size=1200` | 传给 RTP/UDP 输出的包大小设置，促使大 NAL 分片；不是图像大小 |

FFmpeg 各版本的具体日志、随机初始序号/时间戳/SSRC、包数量和字节数可能不同。`pkt_size` 的具体计数层级应结合版本文档和抓包验证；不能直接把此值当作 §7 中抽象定义的“FU 内容字节数”。

### 13.2 Windows：两窗口完整操作

**窗口 A**：切到实验目录，先启动接收器：

```powershell
if ($LASTEXITCODE -ne 0) { throw 'Decode failed' }
ffprobe -v error -f h264 -count_frames -select_streams v:0 -show_entries stream=codec_name,width,height,nb_read_frames -of default=noprint_wrappers=1 live.h264
```

### 13.4 怎样判定成功

先在 `live.sdp` 中确认 `H264/90000`、PT=96 和 `packetization-mode=1`。若你的版本生成了不同 SDP，应先弄清配置差异，不盲用参数 `96 1`。本实验通过 `repeat-headers=1` 发送带内 SPS/PPS；示例程序不会自动从 `live.sdp` 注入参数。

正常应满足：

- 解包输出中能看到 7、8、5、1 等 NAL 类型；也可能有 6、9 等辅助 NAL。
- 解包器 `dropped=0 warnings=0`，退出码为 0。
- `ffmpeg` 解码到空输出没有错误，退出码为 0；`-f null -` 只验证解码，不生成图片文件。
- `ffprobe` 报告 `codec_name=h264`、`width=320`、`height=240`、`nb_read_frames=20`。

若想看画面，Windows 和 Linux 都可在装有 `ffplay` 时执行：

```text

```

裸流没有 MP4 那样完整的时间线；观察窗口是辅助验证，精确原始 RTP 时间信息应另行保存。声音、帧调度和同步不在这一步恢复。生成单张图片可另执行 `ffmpeg -f h264 -i live.h264 -frames:v 1 first.png`。

**实验扩展：**把 `pkt_size=1200` 改为 600 后重新采集并比较 RTP 包数、FU-A 数、NAL 数和解码帧数。通常分片更多，但图像数仍为 20；不要要求 NAL 数等于包数。每次重跑会覆盖本实验的抓取文件，需要对比时先手动另存。

## 15. 接入解码器：参数集、AU 和丢包恢复

### 15.1 把示例放回真正的 RTSP 客户端

**前置：**完成前面的实验；API 细节可等 [[08-FFmpeg与解码]] 再实现。

```text
DESCRIBE → 解析 SDP → 得到轨道、PT、H264/90000、fmtp、参数集
SETUP    → 确定 UDP 端口，或 TCP 的 RTP/RTCP channel
PLAY     → 开始收媒体
    ↓
传输分流 → 完整 RTP 包 → 按轨道/SSRC 分状态 → 校验、去重、重排
    ↓
H.264 RTP 解包 → 完整 NAL → AU 组装/解析 → 解码器 → 像素与显示
```

本章 `parse_rtp` 的输入必须是一个完整 RTP 包。UDP 的一次正常 `recvfrom` 保留数据报边界；TCP `recv` 则可能读到半个或多个交织帧，必须先在 TCP 接收缓存中按外层长度拆出完整内容。

数据边界的职责要明确：传输层不能猜 NAL；解包器不能猜 TCP 消息；解码器不能替你补回丢失的 FU 字节。

### 15.2 从 SDP 拿参数集时怎样注入

**前置：**§3.2、§4、[[04-SDP会话描述]]。

遇到 `sprop-parameter-sets=...,...` 时：

1. 在第一个等号处分割参数名和参数值，保留 Base64 末尾的 `=`。
2. 按逗号拆出各个 Base64 项，逐项解码为二进制 NAL。
3. 验证大小、NAL 类型及参数语法，按参数集 ID 缓存。普通 AVC 初学场景重点关注 SPS=7、PPS=8。
4. 选择当前 Slice/IDR 实际引用的匹配参数集；必要时在该恢复点前输出 `起始码 + SPS`、`起始码 + PPS`，或按所用库的格式设置解码配置。
5. 收到带内更新时同步参数缓存，关注分辨率、profile 等变化。

“注入”只是把解码器需要的配置送到正确接口，不能生成原本不存在的正确参数。不要把 Annex B 起始码格式的参数集直接当成所有解码 API 都接受的 `extradata`；具体格式要求由解码器/容器接口决定。

这里不再实现另一套 Base64 和完整 SPS/PPS 解析器，以免第一次学习偏离 RTP 重组主线。练习可使用已有可靠库解码 Base64，再复用本章 NAL 写入逻辑；不要凭手工编一份参数集给真实码流。

### 15.3 等待关键恢复点：一个保守状态机

**前置：**§3.3、§8。

```text
等待匹配 SPS/PPS
    ↓ 参数可用
等待完整 IDR AU
    ↓ IDR 的全部必要数据到齐
正常解码
    ↓ 确认关键参考数据缺失、参数不兼容或解码持续失败
清理损坏重组/AU，处理解码器旧参考状态，重新等待恢复点
```

进入等待状态后仍要接收数据、更新参数集、寻找下一个完整 IDR，不能把整个网络接收线程停掉。看到第一个类型 5 NAL 也不表示整个 IDR AU 已收齐；多 Slice 的情况尤其要注意。

丢失非参考数据不一定需要完全重启解码器，丢一个 FU 也不一定要重建整条 RTSP 连接。先判断损坏影响；上面的状态机是便于入门的保守策略，不是所有播放器唯一的实现。

### 15.4 关键帧请求不是无条件可用的按钮

RTCP 的 PLI（Picture Loss Indication，图像丢失指示）和 FIR（Full Intra Request，请求帧内刷新）可用于相应反馈机制。是否允许使用、使用什么 RTP profile、反馈参数和发送格式，要按协议协商及设备支持确认；相关内容见 [[06-RTCP协议]]。

发了请求不代表对端立刻返回 IDR，也不能把任意 RTSP `PLAY` 请求理解为“请生成关键帧”。应设置节流和等待策略，不能每丢一包就无休止发送请求。没有反馈能力时，可能只能等周期性恢复点或使用设备明确支持的接口。

### 15.5 何时清解码器，何时重建它

- 未完成 FU：清解包缓存，不把残片交给解码器。
- 已确认 AU 不完整：标记/丢弃对应 AU；参考链受损时进入恢复状态。
- 解码器还保留旧参考图像：按 API 语义处理刷新或重置，避免把旧流状态混到新恢复点。
- 编码参数或分辨率改变：重新评估配置、像素缓冲和显示资源，必要时重建解码上下文。

FFmpeg 的“清除缓冲并重新开始”和“发送空包排空已有输出”不是一回事。下一章要分别学习 `avcodec_flush_buffers`、`avcodec_send_packet`、`avcodec_receive_frame` 的语义；不要靠反复关闭进程掩盖层次错误。

### 15.6 交给 FFmpeg 时不要默认一个 NAL 就是一个 AVPacket

Annex B 文件交给 FFmpeg 命令行时，工具还会做码流解析和访问单元识别。本章按 NAL 写文件能成功，不说明你可以把每个 FU 片段、每个单独 NAL 随意当作解码 API 的完整输入包。

使用 C API 时，应按接口要求提供解码输入边界：可使用合适的 H.264 parser 组装输入，或在你已经可靠形成 AU 时按相应方式送入。媒体 PTS/DTS、时间基、输入缓冲生命期和所需的末尾 padding 也要按库要求设置。一个发送调用后，需要循环取出当前可用输出，不能只调用一次接收函数。

网络 RTP 时间戳、压缩包 PTS/DTS、实际到包时刻、画面显示时刻是不同概念。为了不丢原始时间信息，正式接口宜传递 `{NAL/AU字节, RTP时间戳, 源标识, 完整性}` 等元信息；纯 `.h264` 文件不保留完整的这些关系。

**PTS（显示时间戳）**回答“这张图什么时候显示”，**DTS（解码时间戳）**回答“什么时候按解码顺序处理”。存在图像重排时两者可能不同。**时间基**是时间数字的计量单位，例如 `1/90000` 秒/刻度；不同单位的数值必须先换算，不能直接比较。

**练习：**中途加入一条只有带外 SPS/PPS 的流，本章未经修改的程序能保证播放吗？你应在哪一层补齐配置？

**检查：**

- [ ] 我能说明 SPS/PPS 的两种来源和参数匹配关系。
- [ ] 我会把 FU、AU、解码器参考状态分开处理。
- [ ] 我知道反馈请求需要支持条件，且恢复不只是“收到类型 5”。

## 16. 常见错误：按层排查，先检查证据

**前置：**遇到实验失败时按本表处理，不需要等全部章节学完。

| 现象或报错 | 优先检查什么 | 应怎么验证或修复 |
| --- | --- | --- |
| 找不到 `cl` | 是否在 VS 开发者终端，是否安装 C++ 工作负载 | 打开 Developer PowerShell；或用已安装的 MinGW |
| 找不到 `g++` / `ffmpeg` | PATH、安装位置、终端是否重开 | 用完整路径执行；先运行版本命令 |
| Winsock 未定义引用 / LNK2019 | 缺少链接参数 | MSVC 加 `ws2_32.lib`，MinGW 加 `-lws2_32` |
| `bind` 失败 | 5004 是否已被其他接收器占用 | 关闭旧接收器；若换端口，代码和 URL 都要改 |
| 首包超时 | 是否先启动接收器、地址/端口是否相同 | 重跑两窗口步骤；抓回环接口验证是否真的发包 |
| `Unknown encoder libx264` | FFmpeg 构建是否含该编码器 | 查 `ffmpeg -encoders`，换带所需编码器的构建 |
| `invalid hex byte`，第一行就错 | 文本是否含 BOM、复制了行号、用了 `0x80` | 使用 UTF-8 无 BOM/ASCII，每字节两位，不带 `0x` |
| `short RTP header` 或版本不对 | 输入是否真是 RTP | 别把 `$` 交织头、RTCP、PCAP 文件或文本字符当 RTP |
| `truncated RTP extension` | 扩展长度单位、完整包边界 | 单位是 4 字节；先验证总长度，不能盲目跳过 |
| `invalid STAP NAL length` | 大端读取、是否误含 RTP 头、包是否截断 | 按包内剩余长度校验；不能读到下一包“补长度” |
| `FU continuation without start` | 是否漏首包、乱序、之前报错清了缓存 | 先看序号和前一条日志，再考虑重排 |
| `sequence discontinuity` | 丢失、乱序、重复、源状态混用 | 对照抓包；真实客户端增加有界重排和去重 |
| `FU timestamp or NAL header changed` | 是否跨 NAL/跨源拼接或发送端异常 | 放弃当前重组，核对全部 FU 的元信息 |
| `non-existing PPS referenced` | 参数集未到、ID 不匹配、带外未注入 | 核查 SDP/带内参数和 Slice 引用；别先怀疑像素显示 |
| `Invalid NAL unit` / Slice 错误 | 是否写入了 `7c/85` 等 FU 头，或缺片仍输出 | 对照 §7 的预期字节；用离线样本先隔离算法问题 |
| 有文件但不能播放 | 是否拿 §10 的虚构字节测试播放，是否缺参数/IDR | 虚构字节只验封装；播放验证使用 §13 的真实流 |
| 局部花屏但程序退出 0 | 只证明本程序未检测到异常，不证明所有图像正确 | 增加 AU 完整性、解码错误及参考链监测 |
| 长时间黑屏 | 未等到参数集/完整 IDR、PT 配错、解码器状态错误 | 分别统计选中包、完整 NAL、完整 IDR、解码输出 |
| 画面出来但越来越延迟 | 重排/解码/显示队列无上限或处理赶不上输入 | 测量每层队列长度与耗时，见 [[11-调试与性能优化]] |

推荐记录每包的：轨道、SSRC、seq、ts、PT、M、载荷长度、外层类型；FU 再记录 S/E 和原始类型。日志分清“传输缺口”“非法头”“不支持模式”“不完整 NAL”“解码失败”，比一句“视频错误”更容易定位。

可以先写一行现象记录：“我期待什么，实际什么，最早出现差异在哪层”。如果输出起始码数正常但解码失败，仍应检查内容与参数集；“数目正确”不是“内容正确”。

## 17. 分层练习、参考答案与编程扩展

### 17.1 基础题：先手算，不运行程序

1. `0x67`、`0x68`、`0x7c` 的低五位分别是多少？`0x65` 的 F/NRI/Type 是什么？
2. 一个 NAL 由三个 FU-A 运输。应添加几个原始 NAL 头、几个 Annex B 起始码？
3. `7c 85 11 22` 中哪些是打包头，哪些是 NAL 内容？原始 NAL 头是多少？
4. STAP-A 载荷为 `78 00 02 67 aa 00 03 68 bb cc`，能提取几个 NAL？各是什么？
5. 一帧 30 fps 视频的 10 个包，序号从 1000 到 1009，时间戳都为 90000。下一图常见时间戳是什么？
6. RTP 的 CC=2、X=1、扩展数据 3 个 32 位字，载荷偏移是多少？
7. 模式未声明，能否直接按模式 1 接受 FU-A？
8. E=1、M=0 是否错误？M=1 能否证明之前没丢包？
9. 一张图的两个 Slice 分别长 3000 和 500 字节，最大 RTP 载荷 1200 字节，若使用最简单的“大的 FU-A，小的单 NAL”方案，需要几包？
10. 两个 NAL 长 4 和 2，四字节起始码表示和四字节长度前缀表示各多大？

### 17.2 基础题参考答案

1. 分别是 7、8、28；`65` 为 F=0、NRI=3、Type=5。28 是 FU-A 外层类型。
2. 都是 1 个。NAL 头在 Start 恢复一次，起始码在完整 NAL 输出时添加一次。
3. `7c 85` 是 FU 运输头，`11 22` 是内容片段；恢复出的原始头为 `65`。
4. 两个：`67 aa` 和 `68 bb cc`。长度包含各自 NAL 头，不包含前面的两字节长度字段。
5. 在固定 30 fps、无复杂重排的假设下常为 93000；同一图的 10 个包不逐包加 3000。
6. `12 + 2×4 + 4 + 3×4 = 36` 字节。扩展的 4 字节头不能漏算。
7. 不能。缺省模式为 0；需要确认发送描述和真实行为是否一致。
8. E=1、M=0 可以表示本 AU 的一个非末尾 NAL 结束。M=1 只指示 AU 末包，不证明前面完整。
9. 4 包。FU 内容容量 1198，大 NAL 去掉一字节原头后有 2999 字节，需 `ceil(2999/1198)=3` 个 FU；小 NAL 再用 1 包。不同聚合策略可能改变包数，但不能断言“一图必为两包”。
10. 都是 `4+4+4+2=14` 字节；边界字段的意义不同，大小相同不能证明格式相同。

其他随堂题提示：非法 STAP 长度要拒绝本包，不能读越界或跨包补齐；丢失 102 后不能把 101/103 拼成完整 NAL；正确 SPS/PPS 不能替代 IDR 的参考刷新；只有带外参数集时，需要在配置/解码输入层补齐，当前示例本身不保证可解码。

### 17.3 字节练习：必须有可核对的输出

按 §11.3 做故障注入，然后补充：

1. 把三个 FU 的序号改为 `65535、0、1`，再将最后的单 NAL 改为 2；其他包同步安排为连续序号。重组应正常，不能把回绕当丢包。
2. 用只有 `7c 85` 两字节的 Start 和 `7c 45 55 66` 的 End，输出应为 `00 00 00 01 65 55 66`；空 FU 内容在 RFC 中允许。
3. 将 Start 的 FU header 从 `85` 改成 `a5`，只改变 R 位。接收端应忽略 R，仍恢复原始头 `65`。
4. 构造带 CC、扩展、Padding 的包，验证相同载荷仍得到相同 NAL。分别让扩展超长、Padding=0，确认拒绝。
5. 构造“前一个 NAL 合法、后一个长度非法”的 STAP-A，确认整个聚合包不提交任何 NAL。

提交格式：输入文本、预期字节、实际十六进制、退出码、原因说明。不要只写“测试通过”。

### 17.4 编程扩展 A：反向实现打包

**前置：**已经会解包，再尝试发送端。以下为算法步骤，不是另一份可直接编译的完整程序。

给定一个**不含起始码**的合法 NAL，以及载荷预算 `B`：

```text
若 NAL 字节数 <= B：
    输出单 NAL 载荷，保留原始头
否则，要求 B >= 3：
    indicator = (原始头 & 0xe0) | 28
    从原始 NAL 的第二字节开始，每次取至多 B-2 字节
    fragment_header = 原始头 & 0x1f
    第一个片段加 S=1，最后一个片段加 E=1
    每包载荷 = indicator + fragment_header + 片段内容
```

同一 NAL 各包时间戳相同；序号逐包递增并允许回绕。只有当这个 NAL 同时是 AU 的最后一个 NAL 时，才在其末包设置 M=1。发送端必须知道 AU 边界，不能“每个 FU End 都 M=1”。

先对 §7 的 7 字节 NAL、`B=4` 手算，应得到三个 FU 载荷。再写函数，把产物交给本章解包器，比较还原 NAL 是否逐字节一致。此类闭环验证适合你熟悉 C++ 后巩固位运算与边界处理。

STAP-A 扩展：选取同一适用时间的多个小 NAL，写外层头、每项 16 位大端长度和内容；外层 NRI 按 RFC 6184 取聚合单元 NRI 的最大值，不能任意固定成 `78`。若总长超过预算，改用其他分组策略。

### 17.5 编程扩展 B：把教学程序升级为接收模块

建议按顺序做，不要一次加入所有功能：

1. 按 `(轨道, SSRC)` 管理独立实例，避免多路状态混杂。
2. 在解包前增加有界去重/重排队列，处理迟到包、回绕和超时；不要只用无符号序号的普通大小关系排序。
3. 添加单调时钟超时、最大分片数和资源上限；空 FU 也不能让同一重组无限延长。
4. 在 NAL 上层加入 AU 完整性和恢复状态机。
5. 解析和缓存参数集、接入实际解码器，保留时间信息。
6. 将磁盘输出替换为有界队列或回调，统计每层延迟和丢弃原因。

通过标准：乱序 `101、103、102` 在设定窗口内能恢复；真正缺片时不提交残缺 NAL；多 SSRC 同时输入不串流；持续无 End/空片段攻击不会无限增长资源。这些是工程练习，当前示例未声明实现。
